# The plan: timeline, week sheet, navigation, Now sheet, program weeks, dated plan

Moved verbatim from `CLAUDE.md`. Paths in links are relative to this folder.

### The plan: one timeline

The start page `/` is [PlanPage.tsx](../../src/pages/PlanPage.tsx) (`AppShell title="Plan"`): **one scrolling list over calendar weeks** — the past above as a log (only what was done), today in the middle, the plan below. It replaced Home. Entries are read-only here as everywhere; the page starts only what is open *today*.

- **Range.** From `timelineFirstMonday(today)` (four weeks back, ephemeral `useState`) to `timelineLastMonday(today, loadLastPlanDate())` — the later of next week and the week of the last entry, so an imported twelve-week block is visible to its end without empty weeks behind it. `buildCalendarWeeks` gets `timelineWeekCount(...)` rows, and the whole span is loaded once (`loadPlanBetween`, `loadCompletedSessionsBetween`, `loadRunsBetween`, `loadTestsBetween`, then `loadSessionVolumes` for every done session), in one live query whose result carries the range it was loaded for.
- **Loading earlier weeks, without a jump.** "Frühere Wochen" (`data-load-earlier`, ghost) stands above the first week only while `loadEarliestTimelineDate()` — the earliest local day over completed sessions, runs, tests and entries, each via its index; an aborted session does not count — lies before `firstMonday`. A tap moves `firstMonday` back by `TIMELINE_LOAD_STEP_WEEKS`. Safari has no `overflow-anchor`, so the page anchors by hand: before the shift it remembers the old first week's position in the visible part of its scroll container, and a `useLayoutEffect` adds the difference to that container's `scrollTop` — on every render until the data of the new range has arrived, because the earlier weeks only grow once their units load. Measured through the `offsetTop` chain and the nearest scrolling ancestor (`document.scrollingElement` as fallback), never `getBoundingClientRect` and `window.scrollBy`: in phone landscape `index.css` rotates `#root` by 90° and scrolls its child, so the window does not scroll and client rects run along the physical x axis. The pill's up/down arrow reads the same layout position.
- **Opening on today.** Once everything above the timeline (head lines, load button, range) has loaded, the page calls `scrollIntoView({ block: 'start' })` on the current week's section, once per mount, without animation. Rendering waits for those queries; a head line that appeared afterwards would push today out of view.
- **Week head** ([TimelineWeek.tsx](../../src/components/TimelineWeek.tsx)): a `button`, `sticky top-0 z-10` on `bg-app`, sticky within its own section so the next head pushes it out. `describeTimelineWeekHead` gives the title (`16.–22.11. · W3 · diese Woche`, `truncate`), the counter `{done} von {planned}` (`countWeekProgress`) with a forest bar, and the label (`… · Woche öffnen` as `aria-label`); counter and bar go when nothing is planned. The current week has an ink border. `onOpenWeek(key)` is where the week sheet hangs.
- **Days.** A day with units is a box (`data-timeline-day`) with its own head (`data-timeline-day-head`, `describeTimelineDayHead`): "Mo 23." on the left — today with an ink "heute" pill — and the state on the right: "1 von 4 erledigt" once something is done, otherwise "2 Einheiten · ~29 min" (the minutes only when `loadTemplateMinutes` knows every unit of the day, so never for a run). Today's box is `bg-app` with the same `border-2 border-accent` as the current week's head and always stands, also empty ("nichts geplant" above "Heute trainieren"); other days are a quiet `bg-surface-sunken` box without border. So everything that belongs to a day reads as one group. A day without units, not today, is a thin dashed line "frei".
- **Unit states** ([TimelineUnitRow.tsx](../../src/components/TimelineUnitRow.tsx)), the row is the touch target:

  | Unit | Looks | Tap |
  |---|---|---|
  | done session / run / test | forest (`bg-success`), detail line | `/history/session/:id` / `/runs/:id` / `/tests` |
  | taken by the running session | white, `läuft · Satz 7 von 18` (`loadActiveSessionProgress`) | `/session/:id`, **without** `openFocus` |
  | today, `pickTodayNowEntryId` | the **lime** `NowCard` (`data-now-unit`, `Heute · {name}`), ink mark `Start` / `Eintragen` | workout: `startSessionFromTemplate(id, { planEntryId })` → `navigateToStartedSession`, **a guided workout instead goes to `navigateToGuidedStart`** (see "Guided templates"); run: `RunLogSheet` with `initialPlanEntryId` |
  | today, further open ones | white, text mark `Start` / `Eintragen` | as the lime card |
  | today open while a session runs | white, no mark | `PlanEntrySheet` |
  | planned in the future | white, icon in an ink ring | `PlanEntrySheet` |

  Details come from `describeCalendarUnitDetail` (exercise count from `loadTemplateExerciseCounts`, minutes from `loadTemplateMinutes`). **While a session is `active`, the one lime field is the `ActiveSessionBar`**: the timeline shows no lime card, and today's open entries do not start — a tap only opens the display. A session running without an entry does not appear (the strip shows it); once completed it stands there as `spontan`. A start error shows as an `Alert` above the list.
- **"Heute trainieren".** Today without an open entry gets a dashed ink row (`data-today-free`) with the hint `am längsten her: {name}` (`pickNextTemplate`; no hint without workouts). It calls `setNowSheetOpen(true)` — also when something is already done today. No lime: nothing is due.
- **Head lines**, each a narrow 44px row above the weeks: the backup reminder (`data-backup-reminder`, `warning`, `ShieldAlert`, `1 Training ungesichert` / `{n} Trainings ungesichert`, its "Sichern" button calls `exportDatabaseSnapshot({ preferShare: true })` with the cancel and error handling Home had); the override line (`data-week-override`, only for `weekControl.mode === 'override'`: `Woche von Hand gesetzt: W{n}` and a link "Einstellungen" — it reads, the one writer stays Settings); and the weekday hint (`data-plan-weekday-hint`, the text and target are those of the weekday migration, see "The dated plan").
- **"↓ Heute" pill** (`data-jump-today`, `aria-label="Zu heute springen"`): fixed and centred, with the AppShell's bottom padding as its offset (`7rem`, `10.5rem` with a running session, plus `env(safe-area-inset-bottom)`). It stands while an `IntersectionObserver` says today (`data-timeline-today`) is out of view, its arrow points up when today lies above, and it scrolls to the current week's section.
- **Back to where you were.** Opening a done unit or a run from the timeline (the row, or the `PlanEntrySheet` link to `/history/session/…` / `/runs/…`, **not** `/session/…`) passes `state={{ from: 'plan' }}` (`FROM_PLAN_STATE`, [back-navigation.ts](../../src/lib/back-navigation.ts)). `useBackToOrigin()` reads it: with the mark the "Zurück" of `HistorySessionPage` (and the redirect after deleting a run) is `navigate(-1)`, without it `navigate('/history')` — a deep link or cold start on the detail page must never lead nowhere, and from Fortschritt nothing changes. The page remembers its position in the ephemeral ui-store (`planPosition`: topmost visible `[data-timeline-week]` and its `visibleTop`, plus `firstMondayKey` and `todayKey`), measured on scroll, throttled by `requestAnimationFrame`, **never in the unmount cleanup** (the DOM is already being torn down there). It is restored **only on `POP`** (back button, back gesture, `navigate(-1)`) **on the same day**: `firstMonday` and `scrollAnchor` start from it, the "open on today" scroll is skipped, and the existing scroll compensation puts the anchor week back at its remembered top (it measures the current position and shifts by the difference, so it is absolute on a fresh mount) and only ends when `ready && rangeLoaded`. A tap on the Plan tab (`PUSH`), a cold start, an empty store or another day open on today as before; the week sheet is not reopened.
- **`useTodayKey`** ([useTodayKey.ts](../../src/hooks/useTodayKey.ts)) is the local day as `YYYY-MM-DD`, re-read on `visibilitychange` → `visible`, on `focus` and every minute. An app left open overnight follows the new day in the morning: today, the lime card and the range move with it; `firstMonday` stays.

Test anchors: `data-timeline`, `data-timeline-week` (the Monday) with `data-timeline-week-head` and `data-current`, `data-timeline-day` (the day) and `data-timeline-today`, on the rows `data-day-unit` / `data-unit-state` / `data-plan-entry` / `data-plan-entry-state` (the names the earlier day list carried, kept so the selectors moved along), `data-now-unit`, `data-today-free`, `data-load-earlier`, `data-jump-today`, `data-backup-reminder`, `data-week-override` — read by [plan-timeline.spec.ts](../../e2e/plan-timeline.spec.ts), which also covers the overnight day change with `page.clock`. Because a future "Einheit A" entry on the plan only opens its display, `startSampleSession` starts through the Now sheet, and `openRunLogFromNow` in [e2e/helpers.ts](../../e2e/helpers.ts) replaces Home's "Lauf eintragen".

#### The week sheet

A tap on a week head opens [WeekSheet.tsx](../../src/components/WeekSheet.tsx) — read-only, opened from [PlanPage.tsx](../../src/pages/PlanPage.tsx) with `sheetWeek` (`useState<string | null>`, the Monday). It loads its own week (`loadPlanBetween`, sessions, runs, tests, `loadWeeklyVolume(monday, monday)` and the program tables) and builds the week with `buildCalendarWeeks({ weeks: 1 })`, so the head, the tiles and the prescriptions all come from the functions the timeline already uses. The rules are pure in [week-sheet.ts](../../src/domain/week-sheet.ts) (`buildWeekSheetTiles`, `selectWeekSheetBlocks`, `splitWeekPlanEntries`). Nothing in it writes and nothing in it starts.

- **The week selection is ephemeral `useState`** — never `weekOverride`, never IndexedDB. ‹ › move it by `shiftWindow(parseLocalDate(key), ±1)`, and closing the sheet drops it. *Looking at* week 5 must not mean *training* week 5; that is the same class of bug as Home's arrows, which is why both were fixed in one plan. `week-sheet.spec.ts` pages forward and back and asserts that Settings still shows no override afterwards.
- **No "start workout" beside the prescriptions.** `startSessionFromTemplate` resolves the week through `resolveWeekControl`, *not* through the sheet's week, so a start button next to week-5 numbers would silently train week 3. Starting stays on the timeline's rows and the Now sheet. When the week is hand-set (`mode === 'override'`) and the sheet shows the *current* week, whose program week differs from the effective one, a neutral note says so: `Von Hand auf W{e} gesetzt – ein Start trainiert W{e}, nicht W{n}.` In any other week it would not be true, so it is absent there.
- **The prescriptions disappear where there is no program week** — no active program, no `startedOn`, or a calendar week before week 1 or after the last one; the title is then plain `Woche`. A calendar week without a program week has no prescription, and falling back to `activeWeek` would hang week-3 numbers on an arbitrary Monday. Inside the span, a week without any rules is **not empty**: every workout is listed, collapsed to its disclosure — `alle {k} Übungen wie im Workout` — and that *is* the true answer to "what is planned this week": the same as every other week.
- **Tiles** (`data-week-tile` = kind, `data-tile-done` when `done`): Kraft, Mobility, Laufen, three columns, one column below 360px (Yoga and Faszien count in the Mobility tile, like in `weekly-volume.ts`). A *planned* count is what is **dated** in the week in any state; a *done* count is what the week holds as done units, planned or not. A future week reads `{n} geplant`. A tile with something done is forest (`DONE_SURFACE`), otherwise white — numbers are not a state, so never lime. Side comparisons count in no tile; the test appointment is its own row (`data-week-test`, a link to `/tests`: forest `DoneRow` once measured, otherwise white), shown only for `ProgramWeek.kind === 'test'`, which stays purely descriptive.
- **Block selection.** `selectWeekSheetBlocks` shows the workouts with an entry in the shown week, ordered by their first entry, each with its days (`Mo · erledigt`, `Do · heute`). A week with no workout entries shows every workout, without days — the sheet answers "what is prescribed", not only "what is booked".
- **Disclosure.** Per block, only the rows a week rule overrides are open (`splitWeekPlanEntries`), each with a neutral `W{n}` badge (`data-rule-badge`) — the rule's week, not a state colour. The rest folds into one button with `aria-expanded`, `+ {k} weitere wie im Workout`; expanded, all rows stand in the workout's order (`data-week-row`). The state is an ephemeral `useState` per block. The row rendering is `WeekPrescriptionBlock`, the cards of the former program page, now without an edit handler: rules are edited in the workout under "Wochenprogression", not here.
- **Anchors.** `data-week-sheet` (the Monday, on the body — the title and ‹ › stand in the sheet's header, so read them through `[data-sheet]`), `data-week-tile`, `data-tile-done`, `data-week-test`, `data-week-prescription` (the workout id), `data-rule-badge`, `data-week-row` — read by [week-sheet.spec.ts](../../e2e/week-sheet.spec.ts).

#### Navigation: five entries and a centre button

The bottom bar in [AppShell.tsx](../../src/components/AppShell.tsx) reads Plan (`/`) · Fortschritt (`/history`) · **Jetzt** · Abgleich (`/sync`) · Bestand (`/library`), in a `grid-cols-5`. Jetzt is a `button`, not a link (`aria-label="Jetzt trainieren"`, 48px ink on paper, 16px above the bar — except while a session runs: then the `ActiveSessionBar` sits on top of the nav and the button is flush (`mt-0`) so it does not cover the bar's title and clock) and only calls `setNowSheetOpen(true)`; `NowSheet` resets the flag on every path change. Which tab is active comes from `activeNavTab(pathname)` ([navigation.ts](../../src/lib/navigation.ts)), not from `NavLink`'s `isActive`, so Bestand stays active on `/templates/:id`, `/exercises`, `/bands`, `/tests` and `/programs/manage`; the active link carries `aria-current="page"`. Settings is in the header, not in the bar (`activeNavTab` returns `null` there). [LibraryPage.tsx](../../src/pages/LibraryPage.tsx) is the hub of link rows (Workouts, Übungen, Programm, Bänder, Tests) with counts, and carries no lime and no start buttons.

`/programs` renders nothing any more: it is `<Navigate to="/" replace />`, so an old link or a bookmark lands on the plan, and `activeNavTab` has no special case for it. `/programs/manage` ([ProgramsManagePage.tsx](../../src/pages/ProgramsManagePage.tsx)) is the existing CRUD on `Program` and `ProgramWeek` and stays — a subroute rather than a sheet, because that form carries `ConfirmDialog`s and a dialog inside a sheet is two stacked dialogs, exactly the ambiguity `[data-sheet]` was introduced for. `startedOn` stays in Settings: two writers on the field that drives the calendar week was the original bug.

#### The Now sheet

**`NowSheet` is "Jetzt trainieren", global and independent of the plan.** It replaced `TodayUnitSheet` and is mounted once in [AppShell.tsx](../../src/components/AppShell.tsx) (not under `/session/`, where the focus sheet already lies); `isNowSheetOpen` / `setNowSheetOpen` in the ui-store open it, and the timeline's "Heute trainieren" row is just `setNowSheetOpen(true)`. Top: today's first open workout entry as the screen's one lime row. Then three sections of one-column rows, built by `buildNowSections` in [today-units.ts](../../src/domain/today-units.ts) (recency from `loadTemplateRecency`, `describeLastTrained`, `describePlanDay`): **"Nachholen"** — the open entries of the last `PLAN_SHIFT_WINDOW_DAYS` (7) days, one row per entry, `von Mo · zuletzt …`; **"Spontan"** — every workout without an open entry from today on, by name, `{n} min · {k} Übungen · zuletzt …`; **"Geplant"** — per workout its next open entry from today on, however far away, by date, `heute geplant` / `geplant Do` / `geplant 03.12.`; the lime row's workout is not repeated there. A workout can stand under "Nachholen" and "Geplant" at once — those are two different entries. Anchors: `data-now-section="nachholen|spontan|geplant"`. **No filter and no short tiles any more** (decided 24.11.2026): with a handful of workouts the chips sorted nothing, and "planned or not" is the question that matters; rows wrap instead of `truncate`, pinned by a 320px measurement in `now-sheet.spec.ts`. Then "Erfassen" ("Lauf eintragen", "Test erfassen" → `/tests`; text only, no icon, wrapping instead of `truncate` — two columns of ~140px at 320px clipped "Lauf eintragen" with the icon, pinned by a 320px measurement in `now-sheet.spec.ts`). **While a session runs** (`status === 'active'`, read by `useLiveQuery`), none of that is shown: the sheet has one ink (`accent`, *not* lime) `Link` "Training läuft · zurück" to `/session/<id>` — a plain link **without** the `openFocus` state, because it is a return, not a start — plus the shared `ActiveSessionHint` ([ActiveSessionHint.tsx](../../src/components/ActiveSessionHint.tsx), used only here) explaining why no second workout starts. Lime row, sections and start rows are gone in that state; "Erfassen" stays, those are not session starts. **The minutes are a rough figure for the "Spontan" rows only**: `estimateTemplateMinutes` sums work time per row (`targetSeconds`, else reps × `SECONDS_PER_REP`, else `FALLBACK_WORK_SECONDS`) plus `ROW_OVERHEAD_SECONDS`, both sides plus `SIDE_SWITCH_SECONDS` on a unilateral exercise, one warmup round at `WARMUP_REST_FACTOR` of the rest unless `includeWarmup === false`, and the rest after every round but the last — all constants imported from [session-estimate.ts](../../src/domain/session-estimate.ts), no copies; no progression rule, no history, no pace (that is what `session-estimate.ts` does for the running session). It is read by `loadTemplateMinutes` / `loadTemplateExerciseCounts` in `history-queries.ts`. A guided workout (`TodayUnitOption.guided`) does not start here at all: the tap closes the sheet and `navigateToGuidedStart`s to its start screen, in every start path (Now sheet, plan, `TemplatesPage`, `TemplateDetailPage`). **How a tap starts is `nowStartMode`.** A row whose entry is today starts with `{ planEntryId }` like the timeline's lime card (`link`). A row whose entry lies on another day inside the window asks first (`ask`): a `ConfirmDialog` with `secondaryAction` — "{Name} ist für Do geplant" / "{Name} war für Mo geplant", buttons "Termin vom Do vorziehen" / "Termin vom Mo nachholen", "Zusätzlich trainieren", "Abbrechen". Everything else — "Spontan", and a planned row whose entry is beyond the window — starts without an entry (`extra`). Pulling forward or catching up passes that entry's id; "Zusätzlich" passes none, and without an id a start links only an entry of *today* (see "The dated plan"), so an extra session changes no other day. Decided 24.11.2026: a unit may be trained twice, and whoever pulls a heavy unit forward a day simply ignores it the next day. A session that is already active wins as it always does. "Lauf eintragen" closes this sheet before the run sheet opens — never two sheets stacked; the `RunLogSheet` lives inside `NowSheet`, like on the plan timeline and the run detail (whoever can open it owns it). A plan is an offer, not a lock, so every workout stays one tap away on a day the plan says something else.

#### Restrictions outside the session

Read side in [restriction-queries.ts](../../src/db/restriction-queries.ts), computed like the start (assignment → week rule of the current week → restrictions of today), so nothing here differs from what a start writes.

- **Plan page:** `RestrictionsCard` sits with the head lines above the timeline, only while there are active or announced restrictions (`loadRestrictionCards`; lifted and expired ones are gone). One row per restriction: name, `describeRestrictionPeriod` („bis 14.12.“, „ab 01.12.“, „ohne Enddatum“) and the number of **live** targets. A tap opens `RestrictionSheet`: reason, period, the targets in plain names (`describeRestrictionTargets`: pause with replacement, adjustment with values), dead targets greyed as „gibt es nicht mehr“ (deleted workout, removed assignment, step no longer in its template, deleted exercise) and targets without a hit as „trifft derzeit nichts“ (no workout has the exercise / no guided template has the step) — neither is counted, nothing is deleted. „Aufheben“ goes through a `ConfirmDialog` to `liftRestriction`, the app's only write path for restrictions. Neutral colours, no lime. Anchors: `data-restrictions-card`, `data-restriction-row`, `data-restriction-sheet`, `data-restriction-target`.
- **Workout detail:** each exercise affected today carries a label under its targets (`loadTemplateRestrictionView` → `describePlannedRestriction`: „Pausiert bis 14.12. · Ersatz: Step-up · Beispiel A“, „Angepasst: 40 kg statt 45 · …“, „Steigerung gehalten · …“, „Hinweis · …“, plus notes); a guided template's `GuidedStepsCard` shows the step labels of the start screen (`describeGuidedStepRestrictions`). Information only — the template is unchanged. Anchors: `data-template-restriction`, `data-guided-step-restriction`.
- **Now sheet:** a line under the workout row, „1 Übung pausiert · 1 angepasst“ / „1 Schritt angepasst“ (`loadRestrictionSummaries` → `TodayUnitOption.restrictionSummary`, anchor `data-now-restrictions`). It is computed for **today** for every row: catching up and pulling forward both start today. Only paused and **actually** changed targets count — an adjustment equal to the week value, a note only or a held progression do not (`countRestrictionEffects`).
- **Week sheet:** nothing.

#### Units and program weeks

**A day is made of units, and a unit has two states.** `CalendarUnit` is a `kind` (`strength | mobility | run | test` — a test is a side comparison, a done unit only), a `state` (`geplant | erledigt`), a name and a `ref` — where a tap leads: a completed session, a running session, a run, or the entry itself. **Done comes from history, never from the plan**: a completed session lands on the local day of its `completedAt` (kind from `templateCategorySnapshot`, missing = strength), a run on its `date`, read as the string it is — never through `new Date` (UTC midnight, a day early west of Greenwich) — and both stand even on a day where nothing was planned: the timeline must not contradict reality. A done entry appears **once**, through its session or run, never again as an entry, so an entry done on *another* day no longer stands on its own day. **Planned** is an open entry from today on, its kind the workout's current `category` (`resolveWorkoutCategory`; a deleted workout counts as strength). An **open entry in the past disappears**: `verpasst` and `teilweise` are gone, because the timeline shows what happened and what is coming, and a past entry nobody trained is neither — "missed" was a judgement the plan cannot make, since the unit may well have been trained unmatched another day. The one exception is an entry **taken by a still-running session**: it stays on its own day even when that day is past, as a planned unit reading "Läuft gerade" that leads to `/session/:id` — it is in progress, and hiding it would hide the one thing currently happening. Done units come first (sessions by completion time, then runs), planned ones after by `orderInDay`. `doneDayOf` in [plan.ts](../../src/domain/plan.ts) is the same day rule applied to a `PlanEntryLink`, for the entry sheet's "Erledigt am …".

**Reading is split by what each part needs.** `PlanPage` loads the whole span once. `loadCompletedSessionsBetween` filters `status === 'completed'` (an *aborted* session also carries `completedAt`) and returns `startedAt`, `templateCategorySnapshot` and `planEntryId` — duration, kind, link — but **no volume**: over a span of weeks that would pull every set log into the one query that every unit needs. The volume of the *done* sessions comes from `loadSessionVolumes`, a second step that reads only those sessions' set logs and sums through `sessionExerciseVolume` ([weekly-volume.ts](../../src/domain/weekly-volume.ts)) — the same rule `buildWeeklyVolume` uses, so a session row and the week sheet's total cannot disagree about what counts as a kilogram moved. `loadRunsBetween` returns distance, duration and title, because a row needs more than a date, and `loadTestsBetween` the side comparisons with their measurement moment.

**`programWeekStart` stays the inverse of `deriveProgramWeek`**, and the only one — it only produces the `W…` labels (the week heads of the timeline and the week sheet), by putting every planned week on its Monday. Week *n* starts at `startOfCalendarWeek(parseLocalDate(startedOn))` plus (n−1) × 7 days **via `setDate`**, never via `n * 7 * 24h` — a week across a DST change is 167 or 169 hours, the same reason `isInCalendarWeek` already gives. `parseLocalDate` is exported from [calendar-week.ts](../../src/domain/calendar-week.ts) for it, and that module's header names both directions.

**`ProgramWeek.kind === 'test'` is only *displayed*** — the same descriptive use as the week head's label (`W5 · Deload`). In the week sheet it is the test appointment (`data-week-test`), which links to `/tests` and turns forest once an `ExerciseTest` falls inside that week. Nothing branches on `kind`, and the plan writes nothing at all.

The kinds have one icon each, mapped in one place — [UnitKindIcon.tsx](../../src/components/icons/UnitKindIcon.tsx): `Dumbbell` for strength, `RunIcon` for a run, `Scale` for a test, and the new [MobilityIcon.tsx](../../src/components/icons/MobilityIcon.tsx), self-drawn because lucide has nothing fitting: an open figure with arms spread and a trunk at double stroke weight, chosen over waves and a leaf. Yoga (a figure sitting cross-legged, [YogaIcon.tsx](../../src/components/icons/YogaIcon.tsx)) and Faszien (a roller seen end-on, [FasciaIcon.tsx](../../src/components/icons/FasciaIcon.tsx)) are drawn the same way. `WorkoutCategory` is `strength | mobility | yoga | faszien` ([workout-category.ts](../../src/domain/workout-category.ts), `WORKOUT_CATEGORIES` is the one list the import and backup schemas share); strength is never written, and Mobility, Yoga and Faszien all land in `WeekVolume.mobility` as units without kilo volume. The timeline rows, the week sheet's tiles, the Now sheet's workout rows and the `ActiveSessionBar` all go through it.

#### Editing week rules

[ProgressionRuleFields.tsx](../../src/components/ProgressionRuleFields.tsx) is now used only by `TemplateProgressionSection`, the workout's "Wochenprogression" section, and stays as a **transitional editor until the program import** takes over writing the rules; the week sheet is read-only and has no edit sheet. The form state and the conversion are in [progression-rule-form.ts](../../src/domain/progression-rule-form.ts) (pure, beside the component like `set-log-draft.ts` sits beside the set editor — the field↔record conversion may exist only once). Three things about it: it is built on `TextField`/`SelectField`/`TextArea`, so every field has a real `<label for>` instead of a placeholder that vanishes the moment you type; **the base values are the placeholders**, so an empty field visibly means *as in the workout* — the meaning `foldProgressionRule` gives a missing value; and it is deliberately **not** `ExerciseTargetFields`, which carries `restSeconds` and the work-set count, neither of which a rule can override. Fields the exercise does not have are written as `undefined` (`toProgressionRuleInput`), so switching an exercise to bands later cannot leave a stale kg prescription behind that nobody can see.

**Deload weeks are expressed, not automated.** A `ProgressionRule` may carry `workSetCount` — two sets instead of four is the one field that actually makes a week lighter, and it is part of `foldProgressionRule`, so `materializeSession` writes it into the snapshot *and* into the number of set-log rows it creates (the loop reads the folded value, not the template's). It only ever affects future materializations; a session that has already started has its rows. `ProgramWeek.kind` (`'deload' | 'test'`) sits beside it and is **purely descriptive** — it labels the week head (`W5 · Deload`) and the week in the manage form, and nothing else. Nothing may branch on it: not `materializeSession`, not `resolveWeekControl`, not `startSessionFromTemplate`. The actual reduction stays hand-made through progression rules, and that is exactly what keeps it inside v1, whose contract excludes deload automation. Both fields are additive and unindexed: `.optional()` in `export.ts`, no `SNAPSHOT_SCHEMA_VERSION` bump, no Dexie version. And `updateProgramWeek` takes `kind: null` to *clear* it while a missing key means *don't touch* — `Table.update` deletes any property whose value is `undefined`, so a passed-through `undefined` would silently strip the kind off a week someone only renamed.

[TemplateProgressionSection](../../src/components/TemplateProgressionSection.tsx) **stays** — it is the transposed axis (one exercise × all weeks), which is the right cut for *creating* a progression ("Nordic Curl: 12/14/16/18 s"); its "Plan" link leads to the timeline. Its program `<select>` is gone: rules apply to the **active** program, and a second picker here allowed writing rules into a program that has no effect at all. Its local `formatPrescriptionLine` is gone too, in favour of `describeWeekPrescription` — two formatters are how "3 × 8–10" and "3 x 8 Wdh" end up on two screens.

### The dated plan: single entries, not weekdays

Training is planned as **single dated entries** — `PlanEntry` ([models.ts](../../src/domain/models.ts), table `planEntries`, Dexie `version(6)`), one table for workouts *and* runs, because every reader (timeline, week sheet, export) would otherwise have to merge and sort two sources. An entry is a local day (`YYYY-MM-DD`, read only through `parseLocalDate` and valid only if `toDateInputValue(parseLocalDate(x)) === x` — `parseLocalDate` rolls `2026-02-30` into March), an `orderInDay` (dense from 1), a `kind`, and either a `templateId` or a run prescription: `title` (required), optional distance, duration, elevation, heart rate and pace, `instructions` in the `markdown-lite` subset (written only on a run — `toPlanEntryFields` drops it on a workout, where nothing shows it), plus `notes` on both kinds. The pace **is** stored here, unlike a run's: it is a prescription, and "45 min locker" has no distance to derive it from. Pure rules in [plan.ts](../../src/domain/plan.ts), the shared write helpers in [plan-actions.ts](../../src/db/plan-actions.ts) (`loadTakenPlanEntryIds`, `nextOrderInDay`, `renumberPlanDay`), reads in [plan-queries.ts](../../src/db/plan-queries.ts), UI in the timeline's rows (see "The plan: one timeline") and [PlanEntrySheet.tsx](../../src/components/PlanEntrySheet.tsx), which is **display only** — name and day, the run target and instructions or the workout's exercise count with a "Workout ansehen" link, the notes, and for a taken entry "Erledigt am …" / "Läuft gerade" with its link. **Entries are read-only in the app**: they arrive through the library import (`#/sync`), the weekday data fix and the sample data. Several entries per day are fine; `planEntryKey` — day plus workout, or day plus the run title normalised like `normalizeImportKey` — is the identity, and the same key twice on one day is the duplicate every writer rejects.

Seven rules carry it:

- **Open, taken and done are derived, never stored.** An entry is *taken* when an `active` or `completed` session or any run points at it (`planEntryId`, indexed on both tables); *done* when that is a completed session or a run. An aborted session takes nothing, without anything being written. A stored status would have to be dragged along on abort, on deleting a run and on restoring a backup; derived from the references it cannot lie. The rule exists once per side: `loadTakenPlanEntryIds` for every writer (with `exceptRunId`, so a run being re-saved does not block its own entry), `buildPlanLinks` / `planEntryState` for every reader.
- **A taken entry is history.** The writers that remain (import, data fix) refuse to change or remove it (`PLAN_MESSAGES.taken`), and the check runs inside the same `rw` transaction over entries, sessions and runs, or a session could start between check and write. The dense renumbering of a day after a delete or a date change may still shift a taken entry's `orderInDay` — that number is display order, not history. `deleteTemplate` takes the workout's *open* entries with it; taken ones stay and are named from `templateNameSnapshot` (`planEntryName`). The sheet shows a taken entry with "Erledigt am …" or "Läuft gerade" and a link to its run, its history page once the session is completed, or the running session itself (`/session/:id`) while it is active; it renders nothing until the entry's links have loaded, so a taken entry never flashes up as open.
- **Two linking rules: sessions link only by choice, runs by suggestion.** A session start (`startSessionFromTemplate`, `startGuidedSession`) goes through `pickPlanEntryForStart` in [plan.ts](../../src/domain/plan.ts): an explicit `planEntryId` counts when it is open, belongs to that workout and lies at most `PLAN_SHIFT_WINDOW_DAYS` (7) days before or after today (`isWithinPlanShiftWindow` — a sliding window rather than the calendar week, so Sunday can pull Monday forward and Monday can catch up Sunday); otherwise today's open matching entry; otherwise none, and the session is extra. A start never takes an entry of another day by itself — pulling forward and catching up happen only through the Now sheet's dialog. Until 24.11.2026 a start without id also took the earliest open entry of the current calendar week, future ones included; training Kraft B on Tuesday silently ticked off Thursday, and a second session the same day took the next entry. `findPlanEntryForStart` runs inside the transaction that already checks for an active session, so two fast taps cannot take one entry twice. A stale or out-of-window id **falls back to today's entry** instead of failing — a stale id is no reason not to train. Runs keep `findMatchingPlanEntry`: today's open matching run entry, otherwise the earliest open one of the current calendar week — there the run sheet shows the choice and lets it be changed, so nothing links unseen. The session gets `planEntryId` and `planDateSnapshot`; the program week still comes from `resolveWeekControl`, and `materializeSession` knows nothing of the plan. A run is linked by `createRunLog` / `updateRunLog` (`planEntryId`, `null` unlinks) and carries `runPlanSnapshot` — title, date, targets, instructions — so the run detail can set plan against actual after the entry changes or goes; deleting the run frees the entry by itself. A *new* run in the run sheet preselects through `findMatchingPlanEntry` and offers the open run entries of the run's week plus its own (`loadRunPlanOptions`). *Editing* a run preselects only the entry it already carries and sends `planEntryId` only when the choice was changed by hand — otherwise the key is left out and `updateRunLog` leaves the link alone, so correcting a typo neither links a run silently nor unlinks it. Saving waits until the options have loaded.
- **A series is a copy, not a rule.** Only the sample data still expands one: `expandSeries` ([plan.ts](../../src/domain/plan.ts)) turns weekdays × weeks into individual entries (`setDate` again). Nothing remembers that they were a series, and new entries come in through the import. A recurring rule would be a second plan source that can contradict the first — the class of bug `weekOverride` demonstrated — and the automation v1 excludes.
- **Writes follow the run rules, now for the import and the data fix.** `null` clears a field, a missing key does not touch it, and records are written with `put` of the merged record, never `Table.update` with `undefined`. Messages are `PLAN_MESSAGES`, the same wording in the import and in its preview.
- **Today on the start page is the timeline's business** — the lime card, further open entries, "Heute trainieren" and the rule that nothing starts while a session runs are described in "The plan: one timeline" above. A plan is an offer, not a lock: every workout stays one tap away in the Now sheet.
- **The weekday migration is a data fix, not an `upgrade()`.** `applyWeekdaysToPlanMigration` ([data-fix-actions.ts](../../src/db/data-fix-actions.ts)) turns `scheduledWeekdays` into entries **from today** — never into the past, because a plan invented afterwards would be a claim about training nobody planned — up to the last day of the active program's last week when `startedOn` is set and not expired, otherwise for a chosen number of weeks (default 4) counted from this week's Monday. Same-key entries are skipped, entries within a day go by workout name, and the field is removed from every workout in the same transaction. "Already done" is derived (no workout carries the field), and the dialog names count and range before writing (`previewWeekdaysToPlanMigration`). Until it has run, the plan's head line says so in a neutral row linking to Settings (`data-plan-weekday-hint`) — an empty list would otherwise read as "nothing planned". It asks through `countTemplatesWithWeekdays` in the same module, the question `describeDataFixes` asks, so the field still gets no third reader.

In the backup the table is additive (`.optional().default([])`, the new session and run fields `.optional()`, no `SNAPSHOT_SCHEMA_VERSION` bump), and `templateId` / `planEntryId` are deliberately **not** in `assertReferentialIntegrity`: a taken entry may outlive its workout, and a user's own backup must not fail on that. Restore and the local reset clear `planEntries` with everything else. Test anchors: `data-plan-entry` (the id, on every timeline row that belongs to an entry, done ones included) with `data-plan-entry-state` inside `data-timeline-day`, read by [plan-entries.spec.ts](../../e2e/plan-entries.spec.ts).
