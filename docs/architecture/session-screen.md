# The session screen

Moved verbatim from `CLAUDE.md`. Paths in links are relative to this folder.

### The session screen: list outside, sheet inside

[SessionPage.tsx](../../src/pages/SessionPage.tsx) shows the running workout as a **list of blocks** — one card per exercise, or one per superset group. The sets themselves are not in the list. They live in a **full-height sheet** ([ui/Sheet.tsx](../../src/components/ui/Sheet.tsx)) that opens over it — in a superset, both members, so alternating from set to set needs no view change.

The split exists because the running exercise used to compete with a sticky strip, the card list and the pause bar at once; mid-set you had to search. Now: one exercise, one set, one large action.

- **It opens** on a tap on an exercise row, on the bottom bar, or on a rest chip. **A *fresh* start opens it on the first open block** (decision of 17.11.2026: the detour through the list cost more on short workouts than reading the plan gained). The start callers go through `navigateToStartedSession` ([session-navigation.ts](../../src/lib/session-navigation.ts)), which passes `{ openFocus: true }` as history state; `SessionPage` consumes it once the blocks are loaded (`findNextOpenBlock(blockProgress, '')` → `handleOpenExerciseSheet`) and clears it with `navigate(pathname, { replace: true, state: null })` in every case, so reload and back never reopen it. Returning to a running session (the `ActiveSessionBar`, "Läuft gerade" links) carries no state and **never** opens it, and neither does a timer expiring. E2E: `startSampleSession` closes the sheet again so existing specs start from the list; `session-start-focus.spec.ts` covers the opening.
- **It closes** on swipe-down, the close button and Escape — at any time, in any state — and **by itself after the very last open set of the session**: nothing follows, and the session is ended in the list, as always. Since there is nothing left to wait for, there is no rest mode then either; the pause stands in the list's bottom bar.
- **After the last set of a block it jumps straight into the next open block** (decision of 24.11.2026). `handleSetCompleted` computes the block state from the patched `effectiveLogs` (the live query lags one emit behind), and if the block in the sheet is done, it calls `handleOpenExerciseSheet` on `findNextOpenBlock` ([session-summary.ts](../../src/domain/session-summary.ts)) — behind the current block first, then from the top, never the block itself, skipped exercises count as done; a superset opens as the whole block — or, when nothing is open any more, `handleCloseExerciseSheet`. A switch *within* a superset still runs through `resolveNextFocus` as before. History: until 17.11. the sheet closed here and the next exercise had to be searched for in the list; from 17.11. to 24.11. it stayed open on a finished view (`SessionBlockFinished`: the block on a forest card, a "Danach" line, and the footer button turned into "Weiter: {exercise}" / "Zur Übersicht"), meant as the breather between two exercises — rerack, drink, walk. That breather already *is* the rest mode, which takes over the screen after that set and names the next exercise under "Danach"; the finished view behind it only cost one more tap. Do not bring it back.
- **The rest mode after the last set** still shows the pause of the block just finished, although the sheet already stands on the next one, where no rest runs. `carryOverRestExerciseIds` (ephemeral `useState` in `SessionPage`) holds that block's exercise ids; it is set by `handleSetCompleted` *after* `handleOpenExerciseSheet` (which clears it), and cleared by the next completed set and every manual way in or out (`handleOpenExerciseSheet`, `handleSelectSheetMember`, `handleCloseExerciseSheet`). While it is set, the rest mode takes the latest-ending track among those exercises, and its "Danach" line carries the exercise name in front of the row (`Bulgarian Split Squat · Aufwärmen · links`), since "Satz 1" alone would claim things continue in the exercise the pause belongs to.
- **The big button rests for a moment after the jump.** `isBlockSwitchLocked` disables it for `BLOCK_SWITCH_LOCK_MS` (700 ms): the thumb lies exactly there on the last set, and where "abhaken" stood, "Satz 1 abhaken" of the next exercise now stands — a double tap would tick it before you have seen it. Usually the rest mode covers the sheet anyway, after an exercise without a rest it does not. Test anchors: [session-sheet-continue.spec.ts](../../e2e/session-sheet-continue.spec.ts) covers the jump, the rest mode, the closing after the last block and the superset.
- Its footer is anchored to `window.visualViewport`, not to the sheet's end. Without that, iOS pushes the big button under the keyboard the moment a number field takes focus.
- **The footer also carries its own keyboard bar.** The value fields stand under one another, so once the keyboard is up the second one lies behind it and you had to scroll and tap it. iOS offers no way out of that: the fields carry `inputMode="numeric"` / `"decimal"`, and that keypad has **no return key at all** — `enterKeyHint` alone fires nothing on the device — and an app started from the home screen never gets Safari's own `‹ ›` form bar. [FieldNavigationBar.tsx](../../src/components/ui/FieldNavigationBar.tsx) is that bar rebuilt: back, forward, "Fertig", switched on per sheet (`fieldNavigation` on [Sheet.tsx](../../src/components/ui/Sheet.tsx), opt-in) and present only while a field inside the sheet has focus. The rules are pure in [field-navigation.ts](../../src/lib/field-navigation.ts), in one place because the Return key of a hardware keyboard makes the same jump. Four things are load-bearing. `preventDefault` on **`mousedown`**, not `pointerdown` — without it the tap blurs the field and closes the keyboard under the very jump you asked for, and WebKit sometimes swallows the `click` when `pointerdown` is the one prevented. The bar sits **above** the footer's content, so "below the big button lies nothing but padding" stays literally true and the rest chips keep the sheet's one `role="timer"` — hiding them for the bar would break that invariant in the other direction. The focus is re-read in the **next frame**, because `focusout` fires before the target's `focusin` and a synchronous read would see the body and make the bar flicker on every jump. And it is neutral ink: the one lime field of that screen is already the active set row. Test anchor `data-field-nav`, read by [session-field-nav.spec.ts](../../e2e/session-field-nav.spec.ts).
- Exactly one `role="timer"` stays in the DOM. With the sheet closed that is `renderSessionTimerBar()` in the page's bottom bar; with it open, the stage's set-timer panel while a set runs, otherwise the first rest chip in `renderSheetFooter()`. Both branches read the same `setTimerRemainingSeconds > 0`, so no coordination is needed. Outside the session that one timer is the shell's [ActiveSessionBar.tsx](../../src/components/ActiveSessionBar.tsx), which only renders where the session's own bar does not.
- **You can leave without ending.** The header slot that carries the Einstellungen link everywhere else carries a `ChevronDown` inside a session ("Session minimieren"), and it does nothing but `navigate('/')` — nothing is written, the session stays `active`. Before that, the only ways out of the list were abort, complete, or a detour through Settings. The counterpart is `ActiveSessionBar`: a lime strip above the bottom nav on **every** other screen, showing the template name, the number that is currently being waited on (set timer, else next rest, else session duration — the same ranking as `renderSessionTimerBar`) and the set count, and tapping it anywhere goes back in. Leaving is only cheap if the session is still visible afterwards, which is why the strip is not optional and why the plan carries no resume card of its own (only the taken entry's row, which leads back without opening the sheet).
- The open block is keyed by *block*, but a superset changes its group id when you link or unlink. An effect in `SessionPage` pulls the key back to the focused exercise's block, otherwise the sheet vanishes mid-gesture.
- **Nothing is logged from the list.** Every exercise row — including a finished one on the forest-green card — only opens the sheet. There used to be a check button that ticked the next set straight from the list; it wrote *no* values (set logs are materialized empty), so it silently produced completed sets with nothing in them, and next to the row's own tap target it mostly confused. One path in, one place that writes.
- **Skipping is the one action the list does own**, and it is not an exception to the rule above: it writes no set, it changes the *plan* of this session. `SkipToggleButton` in [SessionBlockCard.tsx](../../src/components/SessionBlockCard.tsx) sits *beside* the row (a button inside a button is invalid) and toggles both ways — `SkipForward` while something is open, `Undo2` once the exercise is skipped; on a finished exercise it disappears, because there is nothing left to skip. It used to live in the sheet's footer, 8px under the check-off button, on exactly the path the thumb travels on its way back from a completed set. You decide to skip an exercise *before* you open it — you are standing in front of the rack and it is taken — so the decision belongs where you see the plan. On the forest-green card the button carries the card's colours and a lime focus ring; the app's ink ring would barely show there.
- **A rest starts only by completing a set.** The bottom bar used to carry a clock button that started one by hand; a rest without a set before it does not happen in training.
- **The header strip carries three numbers, and two of them are a forecast.** `DAUER`, `NOCH` and `ENDE` live in [SessionStatsHeader.tsx](../../src/components/SessionStatsHeader.tsx). The set counter used to be the second column and gave way to the clock time: it is in the sheet's header (`Satz 5 von 18`), which is where you actually read it, every block card carries its own, and the bar under the strip shows the share anyway — whereas the **end time was nowhere**, and that is the number you act on. Not "42 more minutes", but whether you are out of the gym by 19:42. `estimatedEndAt` ([session-estimate.ts](../../src/domain/session-estimate.ts)) is the whole conversion (`now + remainingSeconds`), and it is the *calmer* of the two: while a rest runs, the estimate subtracts the elapsed time, so `remainingSeconds` falls at the same rate `now` rises and the clock time stands still. Only dawdling longer than the next row costs pushes it back — which is exactly the information. One column, two cases: while the session runs it is the forecast, once it is closed it is the **actual** end from `completedAt`, no tilde — so a finished session's strip reads `DAUER | ENDE` and states two facts instead of standing there with a single number. `estimateRemainingSessionSeconds` ([session-estimate.ts](../../src/domain/session-estimate.ts)) sums the plan cost of the open set rows — work time from `targetSeconds` (via `resolveSetTimerSeconds`, so the estimate assumes the number the timer will actually set) or from reps, plus a fixed handling overhead per row, plus one rest **per round rather than per row**: in a superset the partner's rest runs while you work, so only the debt the following work does not already repay is charged, and the pause after the last set of the session is not part of the training. It then rescales that with the measured pace of *this* session — the median ratio of the deltas between consecutive `completedAt` timestamps to what those rows should have cost. No history query: the same template is trained differently on a full Saturday than on an empty Tuesday, and that is already in this session's pace. Three rules are load-bearing: the span from `startedAt` to the first completion is deliberately **not** a sample (it is the walk to the rack), a delta above `MAX_SAMPLE_SECONDS` is an interruption and not a pace, and the measurement only reaches full weight after `FULL_CONFIDENCE_SAMPLES` samples. Between two sets the number ticks down by at most the *next* row's own budget, so idling can never drive it to zero. Skipped exercises drop out entirely, which is why `NOCH` can read "fertig" while the progress bar still counts a skipped exercise's rows — `summarizeSessionProgress` sees only logs, and `toggleSkipSessionExercise` leaves those alone. With nothing open, `estimatedEndAt` returns `null` and the `ENDE` column disappears: "fertig" is a state, not a time.
- **Both numbers follow you into the sheet and into the rest mode**, via [SessionOutlook.tsx](../../src/components/SessionOutlook.tsx) — a leaf that holds its own `useNowTicker`, computes the estimate itself and renders `noch ~42 min` / `bis 19:42`. It sits in the sheet's header beside `Satz n von m` (where the left side truncates and the outlook does not, so 320px holds) and, as an `outlook` **node slot**, above the rest mode's three buttons. The slot keeps `RestMode` purely presentational: it already gets `restLabel` and `nextValues` as finished strings and must not have to know about blocks or set rows to place a line. The ticker is deliberately in the leaf and not on `SessionPage` — that page's `now` is a prop of every block card and of the stage, so ticking it unconditionally would redraw the whole list every second, including while a number field has focus. Two mounted instances therefore compute once a second each; that is accepted, the function is pure and only one of them is ever visible, because the takeover fills the screen.
- **The strip owns its own unconditional 1 s ticker**, like `ActiveSessionBar` and unlike the page. `SessionPage`'s ticker stays conditional on a running rest or set timer, because its `now` is a prop of every block card and the stage — ticking it always would redraw the whole list once a second, including while a number field has focus. Before the split, `DAUER` simply stood still whenever no timer ran.

#### Inside the sheet: one set is big

[SessionExerciseStage.tsx](../../src/components/SessionExerciseStage.tsx) is the exercise with the focus — image thumbnail, name, the current set as value boxes with `−`/`+` around a real `<input>`, then the remaining sets as narrow rows. There is deliberately **no footer line** with volume or last week's numbers: an open set row already shows what you did last time (`setRowFallback`), and a second, truncated listing of the same figures answers nothing. Every other member of the block collapses to a `SessionPartnerRow`: name, set count, rest chips, "Wechseln". Before this, every set stood as a full editor underneath the next — ten fields for a five-set squat, all equally loud, and the number you were actually working on had to be searched for.

Three things about it are load-bearing:

- **`ActiveSetEditor` keeps the old machinery verbatim** — the field-wise draft reconciliation against the live query, the 600 ms autosave, skipping invalid fields instead of writing `undefined`, `adoptPlaceholders` on completion. Only the frame is new. Do not "simplify" it; each of those lines is a bug that already cost data.
- **The value box carries two numbers: the placeholder is last week, the bracket beside it is the plan.** The placeholder comes from `setRowPlaceholders` — last week's values, with the one exception of the time (see "Timers"), where it is the plan — and that is the number you look at in the gym, and precisely why the prescription was being missed: `describeExerciseTarget` states it once, small, in the stage header, half a screen from the figure it has to be compared against. `describeSetTarget` ([session-summary.ts](../../src/domain/session-summary.ts)) is that one field's target — `8–10` via `describeRepRange`, otherwise the plain number, **without a unit**, because the box's `<label>` already carries it, and rendered as `(5)`: a bracket next to a value already says *prescription*, where a stacked "SOLL" label turned the box into a form. It is `text-[15px]`, dropping to 12px below 360px — at 320px there is not 40px left beside `82,5 kg` in 28px, and the bracket would butt against the number that has to stay centred. Five things hold it up. It is deliberately **not `setRowFallback`**: that one is the *default* (last week beats the target) and therefore exactly the number already standing in the placeholder — both slots would show the same thing and the comparison would be gone. It is **absolutely positioned**, so the big number sits exactly where it would without it: that number is what has to be hit from a metre away, and a marginal note that pushes the lead out of centre has swapped the ranking (`session-logging.spec.ts` measures the offset from the box's centre at 320px, which is what keeps it from drifting back into the flow). It stands only on **work sets**, since `3 × 8–10` describes `workSetCount` and a rep target over the warmup row claims something the plan does not say. And it is quiet — `text-content-muted`, no state colour: marking a *deviation* would need a rule for when a range counts as met (8 of `8–10` is not a miss), and "ceiling reached" is what the progression mark two rows up already answers. On the **seconds** field the bracket waits until something is entered: there the placeholder already *is* the plan, so an empty field would show the same number twice. It hangs off the input via `aria-describedby`, never the `aria-label`, which is the handle the e2e grab with `exact: true`. Test anchor: `data-set-target` carrying the field key.

  **In the rest mode the same answer appears only when it is one** — `nextTargetReps` on [RestMode.tsx](../../src/components/RestMode.tsx) (`data-rest-target`), under the big `nextValues`, which is the *default* and usually last week's numbers. The pause is when you stand at the rack and set the thing up, so it is where the question gets asked; but the default usually *is* the plan, and repeating that number underneath itself would be noise. `describeRepTargetDeviation` ([session-summary.ts](../../src/domain/session-summary.ts)) is the whole rule and returns the target only when the row's reps fall outside it — a **range counts as met from within**, so 9 of `8–10` says nothing. That asymmetry against the box is deliberate: there you compare against a field, here you are waiting. Because the line is the exception rather than the rule, it carries the emphasis — the number is large and **lime**, `text-highlight` on the takeover's dark ground, while "Soll" and "Wdh" stay muted paper. That is the **one exception to the one-lime-field rule** (the bar is the other), and it is bought with the fact that the line is absent almost every time; do not take it as licence for a second one. `aria-hidden` like every number there — the accessible statement belongs to the set row in the sheet.
- **How the exercise goes stands under its name, folded to one line.** Until then the sheet showed name, target and rest and nothing else: `Exercise.instructions` and `tempo` appeared only in the library, and the assignment's `notes` ("Direkt nach dem Couch Stretch") were copied into the session by `foldProgressionRule` and then never shown anywhere during training. [ExerciseGuideBlock.tsx](../../src/components/ExerciseGuideBlock.tsx) is a one-line trigger between the stage header and the sets — `AUSFÜHRUNG · {teaser} ›` — that opens [ExerciseInfoDialog.tsx](../../src/components/ExerciseInfoDialog.tsx); the stage's thumbnail opens the same dialog, so picture and instructions are read in one place (the old dark `MediaLightbox` is gone). The rule is pure in [exercise-guide.ts](../../src/domain/exercise-guide.ts). Five things hold it up. The row **shows only the teaser and never expands**, because instructions are read once before the first set, not before every one — an expanded block pushed the value boxes down, and those stay the biggest thing on screen — while a row that reveals nothing never gets opened; so the most important rule belongs on the first line, and without instructions the note, then the tempo, then a lone heading moves up. The dialog sits **above the sheet** (`z-50` over `z-40`), light on paper with no lime (an instruction is not a state), and catches **Escape in the capture phase on `window`** with `stopPropagation` — the sheet listens on `document`, and without that one Escape would close both. Both triggers call `focus()` on themselves before opening, because Safari does not focus a tapped button and the dialog would otherwise return focus to the body; the dialog keeps `onClose` in a ref so `SessionPage`'s once-a-second tick does not re-run its effect. Which exercise has its dialog open is ephemeral `useState` in `SessionPage`, like the sheet. The text is a **small fixed Markdown subset** — `**bold**`, `*italic*`/`_italic_`, `-`/`*`/`1.` lists, `#`–`###` headings (one visual level), blank line = paragraph, single newline = line break — parsed by the pure [markdown-lite.ts](../../src/lib/markdown-lite.ts) into a block tree and rendered by [MarkdownText.tsx](../../src/components/MarkdownText.tsx) as React elements, **never as an HTML string**: links, tables, code and `<b>` stay literal text, so an imported file cannot inject anything. A list is one rule per item; prose stays one paragraph, because cutting it at dots would turn "ca. 90 Grad" into two rules. The teaser is the first non-heading line as plain text, so the most important rule belongs first and the provenance ("Neu seit 30.09.") last; the convention for authors lives outside the repo in `~/Documents/gym-book-daten/anleitungstexte.md`. Instructions and tempo come **live from the library** (`availableExerciseById`, already loaded for the add-exercise form), **not from a snapshot** — they describe how the exercise is done, not what happened, and a correction in the library should show up in a running session; the note stays the session's own copy, labelled "In diesem Workout", since it is true of this workout only. Ink on white, no lime. The dialog sets the text at **17px**, the iOS body size: it is there to be read standing up with the phone in hand, and pinch-zoom is disabled app-wide, so 15px turned the instructions into a footnote; `MarkdownText` headings carry no size of their own and inherit it. The library card and the exercise picker render the same texts through `MarkdownText` (`compact`) — the card at 15px in ink rather than muted grey, because the instructions are the card's content — and the exercise form's textarea names the syntax in its hint. `data-markdown` marks the rendered text for tests. Test anchors `data-exercise-guide` (the row) and `data-exercise-info` (the dialog), read by [exercise-info.spec.ts](../../e2e/exercise-info.spec.ts); the picture case is not e2e-testable, because Playwright's WebKit refuses blob writes to IndexedDB.
- **A mark per set row: "Steigerung möglich".** [progression-hint.ts](../../src/domain/progression-hint.ts) is the whole rule — if, in the last completed execution, **exactly this set number on exactly this side** reached the rep ceiling, the row is marked. No number, no step size, no tap. This replaced a *suggestion* per exercise, and both halves of that change are the same thought.

  **Per set, because the plan is not the only shape training takes.** The predecessor assumed every work set is identical. That holds for 3×8 @ 60 kg and for no other set scheme: on a ramp (set 1: 10×30, set 2: 10×35, set 3: 10×40) it took the **minimum** across all sets and offered 32,5 kg at set 1 — below the actual working load. The minimum is the right answer to *side* differences and the wrong one to *set* differences, and both landed in the same `Math.min`. The per-set cut needs no new plan field, because the history is already set-accurate: `byKey[setLogKey(row)]` in [history.ts](../../src/domain/history.ts). Note **`byKey`, not `resolve`** — the fallback to the highest set of that side is right for a placeholder (any number beats an empty field) and wrong as the basis of a statement about *this* set. Four sets this week against three last week means set 4 carries no mark.

  **Without a number, because the app does not know the gym.** Which jump is possible at the bar, at the dumbbell rack or on the stack is the user's knowledge, not the app's — and dropping the number drops the entire arithmetic: step sizes, rounding, the base across several sets. It also dissolves the old firewall against `setRowFallback` and `adoptPlaceholders`: with no value there is nothing to silently overwrite, and the comments in both places now say that instead.

  What is left of the old rule: the **ceiling** (`supportsReps` → `targetRepsMax ?? targetReps`; `supportsSeconds` → `targetSeconds`, since a time target already *is* a ceiling), `>=` rather than `===`, a missing measurement never counting as achieved, and `nextBandLevel` — on a band exercise the mark only stands while the catalogue holds something heavier, or it would be a lie. Added: `Exercise.suggestProgression` (`undefined` counts as on, only `false` is ever written) switches it off per exercise, for the rotator cuff and the rest of prehab; it is snapshot onto `WorkoutSessionExercise` beside `trackingMode`, so the stage never reloads the `exercises` table. Data still comes from `loadLastValuesForExercises` — **no new query**, one table with two readers.

  On screen it is ink (`bg-accent-soft text-accent`), not lime, because the active set row and the block card already carry the one lime surface. It is large above the value boxes for the one set that is up, and compact (arrow plus one word) on the other rows — four equally loud chips would be wallpaper. The mark **belongs in the accessible name** of the row (`Satz 2 · links auswählen, Steigerung möglich`), not only in an `aria-hidden` arrow; `data-progression-hint` on the row is what `progression-hint.spec.ts` reads.

- **The rep target has three levels**: exercise (`Exercise.defaultTargetReps`, new exercises start at 10) → workout exercise (`targetReps`) → week rule (`foldProgressionRule`, unchanged). The first arrow is a **copy, not a fallback**: `prefillTargetReps` ([exercise-defaults.ts](../../src/domain/exercise-defaults.ts)) fills the field when a workout picks that exercise, and only while it is empty. Changing the exercise default later leaves existing workouts alone — a live fallback would be a number that changes behind the back of a workout somebody finished planning. Two forms assign exercises (the workout and "Übung in der Session ergänzen"), which is why the rule is one function and not two copies.
- **The big button lives in the sheet's footer, its label in the editor.** The footer is anchored to the visual viewport and must stay there; the label ("62,5 kg × 5 abhaken") has to reflect the *draft*, not the stored row, or the button promises something it doesn't write. The editor therefore reports `{label, disabled, run}` upward through `onActionChange`, with `run` behind a ref so the effect only depends on primitives — an object rebuilt per keystroke would loop. It is 62px tall (`min-h-[3.875rem]`), not the 52px it once was, and below it lies nothing but padding: the footer is rest chips, one button, edge. A second full-width control down there competes for the same thumb.
- **Which set is big is derived, not stored**: the manual pick (`selectedSetLogId`) beats the running set timer beats the first open row. A pick from another exercise simply doesn't match, so switching focus needs no reset.

The derivations are pure and tested in [session-summary.ts](../../src/domain/session-summary.ts): block status (`upcoming` / `current` / `done`), **set rows** rather than sets (a unilateral exercise produces two per set number, and both sides are work), `buildSetRounds` (one round = one set number, feeding the header strip, the side cards and the row list), `describeSetPosition` in the block card (`Satz 2 von 4` — rows again, so it agrees with the page header and the block counter), and `describeSetRowValues` against a `setRowFallback` in which last week's values beat the exercise target, because those are what completion actually writes — except the time, where the target wins (see "Timers"). The block card carries its status as `data-block-status`, each set row its id as `data-set-row`, and the header strip `data-session-stats` plus `data-session-estimate` (holding the forecast's quality), `data-session-end` beside it and `data-session-outlook` on the shared line; that is what the e2e tests read instead of guessing at class names — including the one that checks the three columns do not overflow at 320px. The forecast itself lives apart in [session-estimate.ts](../../src/domain/session-estimate.ts): everything here restates what is stored, that module predicts — `estimateRemainingSessionSeconds` the duration, `estimatedEndAt` the same thing as a clock time.

### The plan note banner

A session linked to a plan entry (`planEntryId`) whose entry carries `notes` shows that note in a neutral banner at the top of the session page ([PlanNoteBanner.tsx](../../src/components/PlanNoteBanner.tsx), `data-plan-note`). Before, the note existed only in the plan sheet and nobody read it during training. A tap hides it; that is component state, so a reload brings it back — whether it was read is not training information. The guided start screen shows the note of the entry the start *would* link: the one explicitly chosen in the Now sheet (`location.state`), else today's open entry, through `loadPlanNoteForGuidedStart`, which applies the same `pickPlanEntryForStart` rule and the same taken entries as `findPlanEntryForStart`. Spontaneous sessions without an entry show nothing. Ink, not lime: a note is information, nothing is "up now".
