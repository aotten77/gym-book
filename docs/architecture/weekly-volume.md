### Runs, workout kind and the weekly volume

A **run is not a session.** `RunLog` ([models.ts](../../src/domain/models.ts), table `runLogs`, Dexie `version(5)`, indexed by `date`) is one row: local calendar day, `distanceKm`, `durationSeconds`, optional `elevationGainM`, `averageHeartRate`, `notes`. No sets, no timers, no session snapshots — the contract's "Runs" section says why; the one snapshot a run carries is `runPlanSnapshot`, what its plan entry prescribed (see "The dated plan"). The pace is **never stored**; `paceSecondsPerKm` ([run.ts](../../src/domain/run.ts)) recomputes it, and the pure form state sits beside it in [run-form.ts](../../src/domain/run-form.ts) like `progression-rule-form.ts`. Unlike a completed session a run stays editable: `updateRunLog` ([run-actions.ts](../../src/db/run-actions.ts)) takes `null` to *clear* a field and treats a missing key as *don't touch*, and writes with `put` of the merged record, because `Table.update` would read `undefined` as *delete this property*. The form is a **sheet** ([RunLogSheet.tsx](../../src/components/RunLogSheet.tsx)), not a page, so the keyboard bar of `Sheet` (`fieldNavigation`) carries the number fields. The table is additive in the backup (`.optional().default([])`, no `SNAPSHOT_SCHEMA_VERSION` bump), and its one reference, `planEntryId`, is deliberately left out of `assertReferentialIntegrity`, like every plan reference.

**A workout has a kind**: `WorkoutTemplate.category` (`'strength' | 'mobility'`, [workout-category.ts](../../src/domain/workout-category.ts)). Additive like `tracksHeight`: on the *template* a missing field means strength and strength is never written (`normalizeWorkoutCategory`). The *session* snapshot is different: `materializeSession` always writes `templateCategorySnapshot` (`'strength'` or `'mobility'`), so renaming a workout's kind later does not move history between columns, and "no snapshot" means exactly "started before workout kinds existed"; `applyWorkoutCategoryBackfill` in [data-fix-actions.ts](../../src/db/data-fix-actions.ts) carries the kind onto earlier sessions behind a `ConfirmDialog`, "already done" derived from the data like the other fixes. Nothing in training branches on it — it only separates the weekly calculation.

**The weekly calculation is one function with three readers.** `buildWeeklyVolume` ([weekly-volume.ts](../../src/domain/weekly-volume.ts); `loadWeeklyVolume` in `history-queries.ts` feeds it) turns sessions and runs into `WeekVolume` rows (strength, mobility, running); History, the tiles of the week sheet and the `wochen.csv` of the analysis export all read the same rows — separate calculations are how three screens end up with three different weeks. Selection rule: `status === 'completed'`, a `completedAt` and at least one ticked work-set row — or, for a guided session (`isGuidedSession`, which has no set rows), the completion itself; the week is the local calendar week of `completedAt`. Strength **volume** counts only exercises with `supportsReps` — kilos times seconds is not a kilogram moved; that rule is `sessionExerciseVolume`, shared with the calendar's per-session volume (`loadSessionVolumes`). Mobility contributes units and duration only. Weeks advance via `setDate(+7)`, never milliseconds. `loadWeekSummary` (sessions of the calendar week, with volume) still feeds the workout list (`TemplatesPage`); the week sheet's tiles count by kind through `loadWeeklyVolume`.
