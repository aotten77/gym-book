# Timers and the rest mode

Moved verbatim from `CLAUDE.md`. Paths in links are relative to this folder.

### Timers

Two kinds, both on the running `WorkoutSession` so they survive a reload: `restTimers` (pauses between sets) and `setTimer` (a set *on* time, e.g. a 2-minute plank). At most one `setTimer` per session — starting another replaces it. Its duration comes from `resolveSetTimerSeconds` ([set-timer.ts](../../src/domain/set-timer.ts)): the seconds entered in the set beat the row's prescription, which beats the default. That prescription is **`setRowFallback`, not `exercise.targetSeconds`** — the same value the field shows as its placeholder and the check-off button promises. Reading the exercise target directly was a bug: the field was prefilled with last week's 45 s while the countdown stood at the exercise's 18 s, so that number had to be typed in again to make the timer use it. `session-estimate.ts` is the one caller that legitimately passes the bare target — it plans without a history query and says so.

**For the time, the plan beats last week** — the one field where `setRowFallback` turns the usual ranking round (`targetSeconds ?? lastValues.seconds`). The seconds field is both the *setting* of the clock and the *result*, and since the countdown runs into overtime the result can exceed the setting: a balance held 30 s against a 20 s target set the clock to 30 next time, and the next overtime to 40 — a silent ratchet, which is the adaptive progression the v1 contract excludes. Overtime stays a measurement in the history; whether the time should grow is what "Steigerung möglich" answers and the plan decides. Three things carry it. `setRowPlaceholders` beside it is the same rule for the field's placeholder and for `adoptPlaceholders` on check-off, or the field would read 30 while the clock runs 20, and checking off without a timer would write the 30 the button did not promise; with a target it holds even without any history. Without a `targetSeconds` nothing changes — there is no plan to fall back on, so last week stays the default. And last week stays **one tap away**: `lastSecondsOffer` returns its time when it differs from the target, and the stage shows it under the empty seconds field as a neutral chip, `zuletzt 30 s übernehmen` (`data-last-seconds`), which writes it into the field so both start buttons run on it — whether with cues stays a choice of its own. A **third start button** for "plan time with cues" was considered and rejected: it would have left the field and the plain button on the ratcheted value, and duration and cues are separate questions, so buttons for both would be four.

**The countdown does not end at zero.** It used to: the expiry wrote `durationSeconds` into the set log and cleared the timer, so every timed set held exactly its prescription and the seconds curve was a flat line — a plank you held 17 s longer was invisible. Past zero the clock now counts **up**, shown as `+00:12` (a plus, not a minus: beyond the target you are over it, not short), and the value is written when *you* stop. `overtimeSetTimerSeconds` is that count and it is capped at `SET_TIMER_MAX_OVERTIME_SECONDS` (2 min), because no clock ticks in the background while the timestamps run on — without a cap a forgotten timer would write fourteen minutes into the set. `finishSetTimer` writes the achieved time and clears the timer — `elapsedSetTimerSeconds`, which is duration minus remaining plus overtime under that same cap; `clearSetTimer` drops it without writing. Two consequences. Whether a set timer is running is now `isSetTimerActive` (the timer **exists** on the session) and no longer `remainingSetTimerSeconds > 0` — in overtime the remainder is 0, and the old predicate would drop the clock out of the bar at exactly the interesting moment and break the one-`role="timer"` rule in both directions. And the footer's check-off label reads the running clock instead of the field while a timer belongs to that row, or the button would promise "45s abhaken" and write 57. Anything that invalidates the target (deleting the set log, closing the session) must clear it too, otherwise the bar keeps counting toward a row that no longer exists.

**A set on time also announces itself halfway through**, because during a Dead Bug you lie on the floor and the remaining time only exists on a screen you cannot see. [set-timer-cues.ts](../../src/domain/set-timer-cues.ts) decides *which* cue is due; [speech.ts](../../src/lib/speech.ts) says it out loud ("Halbzeit", "Noch zehn Sekunden" — the number spelled out so no voice reads "ten"), and `SessionPage` vibrates a pattern of its own beside it. Note the inversion against the expiry signal: **Safari on iOS has no Vibration API at all**, so both `navigator.vibrate` calls in that file are no-ops on the target device and the speech is the only channel that arrives. **Whether a run is announced is chosen at the moment you start it, not in Settings**: there are *two* start buttons under the value fields — `Play` starts silently, `Megaphone` starts the same timer with cues — and the choice is persisted as `cuesEnabled` on the `SetTimerState` itself, so a reload mid-plank does not lose it. That is the whole switch; there is deliberately no global toggle, because a preference set once would silently change what the plain button does, and the answer genuinely differs set by set (headphones in, or a full gym). The second button sits in a `grid grid-cols-[minmax(0,1fr)_3.25rem]`, the same 52px column as the `−`/`+` above it, and it is a `Button` rather than an `IconButton` — the latter is fixed at 44px and `rounded-control` and has no `secondary` variant, so it matched neither the height nor the corner of the start button. Settings keeps only "Ansage testen", which answers the one question that is not per-set: can this device read aloud at all. A **headphone detection** was investigated first and rejected: `AudioContext.outputLatency` really does report 0 ms on the speaker and ~15 ms on headphones, but that is an undocumented side effect Apple never promised, and a silent iOS change would take the announcements with it. Don't reach for it again.

Four things are load-bearing. The module compares **timestamps**, not `remainingSetTimerSeconds`: that helper ceils, so a 45 s half-time sits at 22.5 s remaining and `=== 23` would only be observable in a 500 ms sliver of a display second, while `=== 10` loses the cue outright the moment a throttled tick steps 11 → 9. Phrased as a crossing (`dueAt <= now`, like `isRestTrackReady`) any later tick catches it, and `setTimerCueKey` plus a remembered key does the de-duplication — the key carries `endsAt`, so discarding and restarting the same set is announced again. The **thresholds differ** (half only from 45 s, the ten-second mark from 25 s) so two announcements can never land within seconds of each other; the guard against that is in the code, not only in the thresholds, so both stay tunable. Freshness is **2 s and gates the vibration too** — unlike `isChimeFresh`, which lets a late expiry buzz anyway: "the timer is over" stays true forever, "ten seconds left" is a position in a countdown and rots, and someone pacing themselves by it from the floor would let go at the wrong moment. Consequence, intended: after the app returns from the background no cue fires at all, only the expiry. And the **expiry announces itself too, but a beat after the chime.** It used to be chime-only, on the argument that speech and the `AudioContext` in the same instant are the one combination that can cost the existing signal and that the verbal warning had already happened where you could still act on it. The second half didn't hold on a real device: the two-tone is exactly the signal that goes missing — loud room, ringer switch on silent, phone on the mat, and on iOS no vibration beside it at all. So `SET_TIMER_END_SPEECH` ("Ende") now follows the chime after `EXPIRY_SPEECH_DELAY_MS` (700 ms, against a two-tone that runs ~490 ms), which keeps both channels *and* the boundary the chime marks sharply — it rings first, the word confirms afterwards. Four rules. It is **gated on `cuesEnabled`**, the same per-run choice as the two cues, which also guarantees `primeTimerSpeech()` has run. It carries the **same freshness as the chime** (`isChimeFresh` against `realNow`), or an app returning from the background would say "Ende" for a timer that expired twenty minutes ago. The **delay is dropped when `soundEnabled` is off** — with no chime there is nothing to step around. And the text lives in [timer-notifications.ts](../../src/domain/timer-notifications.ts), **not** as a third `SetTimerCue`: `findDueSetTimerCue` returns `null` from `endsAt` onward on the stated principle that the expiry moment belongs to the expiry signal, and a `'end'` cue would break that module's own promise. The expiry therefore has to be fished back out of `expiries` by its key, where it otherwise sits indistinguishable next to the rests — a rest gets no "Ende", it is the moment things resume. The delay itself is executed in `speakTimerAnnouncement(text, delayMs)` rather than in `SessionPage`, whose signal effect re-runs every second and whose cleanup would cut the waiting announcement off before it is due.

**The rest timer is multi-track**, and that is the whole point. A `RestTimerTrack` belongs to a pair of (`sessionExerciseId`, `side`), never to the session as a whole — the old scalar `restTimerEndsAt` had no owner, so every completed set overwrote it. Two cases need this and are the *same* case: in a superset the pause of the first exercise keeps running while the second is executed, and on a unilateral exercise the right side rests while the left is trained. Switching back must show the right countdown. `restTrackKey` is the identity; `upsertRestTrack` replaces same-key tracks instead of stacking them. Pure helpers live in [rest-timer.ts](../../src/domain/rest-timer.ts), built like `set-timer.ts` (`now` as a parameter, no clock inside).

Three display levels, all fed from the same tracks: a badge on the **next open set row** of that side (`buildRestBadges`), chips on non-focused exercise cards, and the bottom bar. The bar shows one track large — `selectPrimaryRestTrack`, which prefers the side of the focused exercise's next open set — and the rest as tappable chips. Exactly **one** `role="timer"` stays in the DOM; several live regions counting down at once make a screen reader unusable.

#### The rest mode

On top of all three sits the **Ruhemodus**: [RestMode.tsx](../../src/components/RestMode.tsx) turns a running rest into a state of its own — full screen, paper ground, the time huge, a bar that fills as the pause runs down, what comes next ("DANACH · SATZ 2" over a large "82,5 kg × 5"), and three actions (−15 s, Weiter, +30 s). During a rest the phone lies on the floor or the bench, and from a metre away the number in the bar at the bottom edge is unreadable.

Several predecessors tried to solve that with a big number *over* the sets — a slanted watermark, then a translucent number in a progress ring. Every one of them had to trade legibility against occlusion and lost one of the two. Here the trade disappears: while you wait, the screen belongs to the pause, and the moment you want to do something else it **collapses into a tab at the edge**, like a minimised video.

- **The tab hangs half outside the frame.** What overhangs covers nothing, and the half that stays carries exactly one number. It can be dragged, snaps to the nearer edge on release (`data-rest-widget` says which one, and the content aligns towards the centre of the screen), and arrow keys move it too — a widget that only answers to a finger is not one. The rules are pure and tested in [edge-widget.ts](../../src/lib/edge-widget.ts); the component measures, that module decides. It starts in the lower third on purpose: at half height sit the value fields whose −/+ are the very reason you put the pause away.
- **It is the one dark surface in the app.** Ground `bg-accent`, text `text-accent-contrast` — ink and paper simply swap roles, no colour invented. The reason is energy: the screen stays on for minutes while nobody uses it, and on OLED a bright field costs current. Three consequences. The bar fills in `highlight` — on ink, lime finally works as a line, which it never could on paper (1.3:1), and it is the only lime on that screen, so rule 1 holds. Every control sets `focus-visible:ring-accent-contrast`: the app's focus ring is ink and would be invisible here, and the `:where()` baseline in [index.css](../../src/index.css) is ink too. And `applyThemeColor` ([theme-color.ts](../../src/lib/theme-color.ts)) swaps `<meta name="theme-color">` to `#0c1210` while the takeover stands, because iOS otherwise keeps drawing the light app's dark status-bar text over it — the device clock would be unreadable for the whole pause. Restoring it is the effect's cleanup, so minimising and ending both put paper back. **This is a deliberate exception to the single-theme rule**, one of two (the other is the guided stage, see "Guided templates"): it is a transient full-screen state, not a second theme, and nothing else in the app may grow a dark variant off the back of it. (The saving only applies to OLED — iPhone X and newer, but not XR and 11.)
- **The minimise button is the session's.** `ChevronDown` in a 48px frame, exactly like the one in [AppShell.tsx](../../src/components/AppShell.tsx) that minimises a running session. "Keeps running, I'm only putting it down" means the same thing everywhere in this app and therefore looks the same.
- **The full state is a dialog, the tab is not.** Only the takeover accepts input; with the tab out, everything under it stays operable — that is the whole point. `role="timer"` stays in the bar in both cases; the numbers here are `aria-hidden`.
- **Minimising sticks for that pause, not beyond it.** `minimizedRestKey` in [ui-store.ts](../../src/store/ui-store.ts) holds the track key (exercise + side), so "+30 s" does not make the takeover jump back up, while every *new* pause opens it again. The key only counts while the rest is **running** — expired tracks linger as "bereit" (`pruneRestTracks`), and hanging the key on those would keep that exercise and side collapsed forever. Ephemeral like `openSessionBlockKey`: after a reload the pause runs on and the Ruhemodus stands open again.
- **The numbers of the coming set carry the size, not their heading.** "Danach" plus the set is an 11px caption; underneath sits `82,5 kg × 5` at `min(12vw,6.5vh)`. It was the other way round — a bold "Danach: Satz 2" over 14px small print — and that is the wrong ranking: *which* set is next you know anyway, but how much has to go on the bar is the one thing you look over for, from the floor where the phone lies. Without values (`describeSetRowValues` can return an empty string) the label keeps the size itself, because a caption alone would be nothing at a metre. The e2e asserts both the absolute size and the ratio to the caption, so the hierarchy cannot silently flip back.
- **Under those numbers, the progression mark, if the coming set carries one** — `nextHint`, so the plate can go on during the rest instead of after it. Display only: the three actions stay three, and the mark is not a fourth. It is `text-accent-contrast/70` like the "Danach ·" caption above it and deliberately **not** lime — the progress bar stays the only lime on that screen — and `aria-hidden` like every other number here, because the accessible statement belongs to the set row in the sheet.
- **One quiet line sits above the actions**: the session's `noch ~42 min · Ende 19:42`, `text-accent-contrast/70` and no lime, so the bar stays the only lime field on that screen. It competes with neither the huge pause number nor "Danach", and during a rest you have the time to read it. The minimised tab gets **nothing** of it — it carries exactly one number, and that is the pause.
- **Two step buttons flank the action**: `−15 s`, `Weiter`, `+30 s` — less to the left, more to the right, like the `−`/`+` around a value field. The steps differ on purpose (`REST_TIMER_SHORTEN_SECONDS` vs `REST_TIMER_STEP_SECONDS`): you extend in blocks because the set was heavy, you shorten because you can already go again, and a step that big would skip the rest of the pause entirely. `extendRestTimer` takes the negative delta and **refuses to cross zero** — a track that expires in the same moment reports an expiry nobody waited out, chime and vibration included; below one step the button is disabled and "Weiter" is right there.
- **It belongs to the sheet** — `SessionPage` mounts it only while a block is open, and only for the clock of the set row that is up (`findRestTrack` on that row's exercise and side). In the list you have the session in front of you and the bottom bar carries the time. The set timer is deliberately **not** part of it: the Ruhemodus is the state of waiting, and while a set runs on time you are not waiting but holding — that clock stays on the stage, next to the set it belongs to.

Because the takeover opens on every check-off, `completeActiveSet` in [e2e/helpers.ts](../../e2e/helpers.ts) puts it away again, and every helper that reaches into the sheet does the same first; the sheet itself is addressed by `[data-sheet]`, since "any dialog" now hits two. The takeover, the drag and the round trip are covered by [session-rest-mode.spec.ts](../../e2e/session-rest-mode.spec.ts).

An expired track is not deleted. It stays as "bereit" — that is the answer people come back for — until `pruneRestTracks` drops it after `REST_TRACK_GRACE_SECONDS`. That grace needs a **ticker of its own**: `SessionPage` calls `pruneRestTimers` every `REST_PRUNE_INTERVAL_MS` (and once immediately) while any track exists. Hanging the call on the expiry effect instead — as it once did — can never clear anything, because in the second a track expires its grace is zero seconds old and no second occasion follows; a "bereit" chip then stood until the next rest start happened to prune on write. Tapping a ready chip clears its track (`handleFocusRestTrack`): the message has been delivered, and it is the only manual way out, since the bar's cancel button only ever gets a *running* track. Vibration fires once per track, tracked in a `useRef` in `SessionPage` (ephemeral on purpose; a reload costs at most one buzz).

**Which of the three signals fires is decided in one place.** [timer-notifications.ts](../../src/domain/timer-notifications.ts) takes the rest tracks, the set timer, both clocks and the set of already-reported keys, and answers `{vibrate, chime, speak, finishSetTimerSeconds, notifiedKeys}`; `SessionPage` holds a single effect that only executes it. Three things about that. It takes **two clocks**, not one: the ticked `now` decides *whether* something is due, a freshly read `Date.now()` decides whether it is still *current* — with one clock, the first tick after returning from the background would report an hour-old expiry as if it had just happened. De-duplication is the **key set**, and every key carries its `endsAt`, so a `+30 s` on a rest or a restarted set timer reports again while a re-render does not; keys that no longer apply are forgotten, which is what lets the same track report after a fresh start. `finishSetTimerSeconds` no longer rides on the expiry: the expiry is the **signal**, and the write happens only at the overtime cap, under a key of its own and gated on `realNow` like the chime — if the app reached that cap in the background, nobody held two minutes over, so the clock stands at `+02:00` and waits for a stop rather than inventing a number. And signals are **coalesced rather than stacked**: two rests expiring in the same tick — or a rest and the set timer — are one buzz and one chime, because two two-tone chimes laid over each other are mush, not a double hint. An expiry outranks a cue for the vibration and the cue is still spoken, since they concern different exercises.

Both expiries also play a sound, from [sound.ts](../../src/lib/sound.ts) — a synthesized two-tone chime, no audio asset the service worker would have to cache. Three things about it are load-bearing. A browser starts an `AudioContext` suspended and only unlocks it inside a user gesture, which a timer expiry is not: `primeTimerSound` runs on `SessionPage` mount and hangs itself on the next touch (on iOS `resume()` alone is unreliable — a silent buffer has to actually start inside the gesture). **Unlocking once is not enough**, and getting that wrong cost the chime entirely: iOS suspends the context again on every trip to the background — app switcher, a pulled-down notification, a brief lock — and the unlock listeners had removed themselves after their one success, so from then on every expiry was silent while "Ton testen" still rang, because that path awaits `resume()` inside a gesture. Two things now re-arm: the context's own `statechange`, and returning to `visible` (which also retries `resume()` straight away — WebKit often allows it there without a touch). And `playTimerChime` no longer gives up on a sleeping context; it resumes and *then* plays, but only if that took less than `RESUME_GRACE_MS` — a `resume()` that is really waiting for the next touch would otherwise deliver the chime minutes late, which is the very fright the rule below prevents. `isChimeFresh` suppresses the chime when the expiry is more than `CHIME_MAX_DELAY_MS` old, because no clock ticks while the app is backgrounded and a chime for a pause that ended ten minutes ago is a fright, not a hint — which is why the expired-track key carries its `endsAt`. That predicate is a *decision*, not a sound, so it lives in [timer-notifications.ts](../../src/domain/timer-notifications.ts) with the rest of them; `sound.ts` only plays. And the sound never replaces the vibration: WebKit plays nothing while the ringer switch is on silent. `AppSettings.timerSoundEnabled` switches it off (additive, `undefined` counts as on), edited via `ToggleField` in Settings — `CheckboxField` cannot be used there because the accessibility e2e measures the control itself and its 20px box fails the 44px rule.

That freshness rule is also why the screen has to stay on. A blanked iOS display freezes the web app — no interval ticks and the `AudioContext` is suspended — so a 60-second set timer expires unheard and `isChimeFresh` then correctly suppresses the late chime on unlock. [wake-lock.ts](../../src/lib/wake-lock.ts) holds a `navigator.wakeLock` screen sentinel for exactly as long as a session is `active`, switched by `AppSettings.keepScreenAwakeEnabled` (additive again, `undefined` counts as on; Safari has the API from iOS 16.4, and Settings disables the toggle where it is missing). Three things about it: the lock lives in [AppShell.tsx](../../src/components/AppShell.tsx), not on `SessionPage`, because a **minimized** session keeps running and its timers with it; the system revokes the sentinel every time the document goes hidden, so it must be re-requested on `visibilitychange` or it is gone for the rest of the workout after the first manual lock; and it is deliberately *not* released between timers — you put the phone down between sets and still want to read the pause. `keepScreenAwake()` returns its own release function and keys its effect on `activeSession?.id`, not the session object, whose identity `useLiveQuery` replaces after every completed set.
