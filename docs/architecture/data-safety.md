# Data loss on iOS

Moved verbatim from `CLAUDE.md`. Paths in links are relative to this folder.

### Data loss on iOS — why the safeguards exist

A home-screen web app on iOS owns a storage container separate from Safari, and **deleting the icon deletes IndexedDB with it**. This already cost a user their training history, because the only way they found to update the app was to remove and re-add it. Three mechanisms follow from that, and none of them is decorative:

- `onRegisteredSW` in [main.tsx](../../src/main.tsx) calls `registration.update()` on start, on `visibilitychange`, and every 30 minutes. Without it the "Update verfügbar" banner never appears in an installed app — a service worker only looks for a new version when the page loads, and a standalone app sits in the app switcher for days.
- **An expired Cloudflare Access session is the one failure that hides itself, so the app says so and offers the way out.** Access answers every request with a redirect to its login page once the session is over — including the one `registration.update()` makes for `sw.js`, and a service worker script may not be redirected, so the check dies with a `SecurityError` and the update banner never appears. Nothing shows: the worker serves every navigation from the precache, so the app never reaches Access and therefore never renews the cookie either. It cannot get out on its own. [access-session.ts](../../src/lib/access-session.ts) probes **`sw.js` itself** with `redirect: 'manual'` — the same file the update fetches, so it fails on the same obstacle and no other; it is neither precached nor a navigation, so the worker leaves it alone. An `opaqueredirect` means expired; a thrown fetch means `unknown`, never expired, because being offline is this app's normal state and the banner must not stand in a gym with no signal. `main.tsx` runs it only when the update check *fails*, and clears the flag when one succeeds. The banner sits above the update banner in [AppShell.tsx](../../src/components/AppShell.tsx) (`data-access-expired`), in ink rather than `danger` — nothing is lost, the app keeps working, it just stops learning about new versions. Its button does a real **navigation** to `ACCESS_LOGIN_PATH` (`/?reauth=1`), never a reload: only a top-level navigation passes through the login, and only there does Cloudflare set the cookie. That is what `navigateFallbackDenylist` in [vite.config.ts](../../vite.config.ts) is for, and it needs **both** entries — `/[?&]reauth=1/` for the request that starts the flow and `/^\/cdn-cgi\//` for the callback Cloudflare returns to. Miss the second and the navigation route answers the callback out of the precache, the cookie is never set, and the flow dies one step before the end; that exact mistake showed up in the WebKit reproduction before the paths were made real. Note what this does **not** fix: a device already stuck runs an old worker without the denylist, so it cannot be rescued from inside — that costs a backup, a reinstall and a restore.
- **Settings names the build that is running**, in a full-width "Version" tile under App-Status: the short commit hash, the commit subject and its date. An updated PWA looks exactly like the old one, and most changes are not visible at a glance, so whether an update actually arrived used to be guesswork. `vite.config.ts` reads `git` at build time and writes it into the bundle via `define` as `__BUILD_INFO__`; [build-info.ts](../../src/lib/build-info.ts) reads it. Three details. It shows what *this bundle* is, not what was last deployed — precisely the question when the service worker is stuck. A local build with uncommitted changes gets a `+` after the hash, because the commit alone would not describe the running code. And vitest has no `define`, so `readBuildInfo` guards with `typeof` and returns `null` there; that the hash really arrives is asserted by [build-version.spec.ts](../../e2e/build-version.spec.ts) (`data-build-version`, `data-build-commit`). A missing git never fails the build — the tile then says so.
- `requestPersistentStorage` ([src/lib/storage.ts](../../src/lib/storage.ts)) runs on every start; Settings shows the resulting state plus usage. It stops eviction under storage pressure, *not* deletion of the app.
- `AppSettings.lastBackupAt` drives the reminder at the head of the plan. `evaluateBackupStatus` ([src/domain/backup.ts](../../src/domain/backup.ts)) counts completed sessions newer than the last backup — elapsed days alone would nag people who simply didn't train. `exportDatabaseSnapshot` sets the timestamp itself, so every export path counts.

`exportDatabaseSnapshot({ preferShare: true })` routes through the Web Share API **only** in `display-mode: standalone`, where iOS hides the download folder; in a tab it downloads, and `navigator.share` would hang there without a share sheet. A cancelled share returns `'cancelled'` and must not mark a backup as done.
