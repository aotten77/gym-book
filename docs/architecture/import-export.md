# Export, import, analysis export, library import, data fixes

Moved verbatim from `CLAUDE.md`. Paths in links are relative to this folder.

### Export / import

[src/lib/export.ts](../../src/lib/export.ts) is the backup format: a full versioned snapshot of every table. Import validates three things, all required by the contract: schema version, referential integrity across tables, and supported media types. `SNAPSHOT_SCHEMA_VERSION` is pinned with `z.literal(...)` — a schema change means bumping the version *and* the literal. `restoreDatabaseSnapshot` clears all tables before bulk-inserting (child tables first); the Settings page exports a backup automatically before restoring. Purely *additive* tables and fields (`bandLevels`, `libraryImports`, `runLogs`, `planEntries`, `Program.startedOn`, `WorkoutTemplate.steps`) go in as `z.array(...).optional().default([])` / `.optional()` **without** a version bump — the literal would otherwise reject every backup a user already has.

### The analysis export — a second export that throws things away

Both entry points — "Analyse kopieren" and "Als ZIP teilen" — live on the reconciliation page `/sync` ([SyncPage.tsx](../../src/pages/SyncPage.tsx), "Abgleich"), no longer in Settings: the plan is written in a claude.ai project, so the loop is one tap to copy, then paste into the thread, and the import comes back the same way. The page reads `loadSyncActivitySince` (raw lists, the fine rule stays in `describeSyncStatus`) and only writes through `copyAnalysisSnapshot` and the import.

The backup answers "can I restore this?". It cannot answer "am I stagnating?": 5,2 MB of it are 25 images as base64 data URLs, 85 % of the set logs are empty placeholder rows from sessions that were started and abandoned, and every question begins with three joins over 36-character UUIDs. Net, five trainable sessions.

Beside it therefore sits **`exportAnalysisSnapshot`** ([lib/export.ts](../../src/lib/export.ts)) — a ZIP with eight files: `sessions.csv`, `progression.csv`, `tests.csv`, `wochen.csv`, `laeufe.csv`, `plan.csv`, `meta.json` and `bestand.json`, built by the pure `buildAnalysisExport` ([domain/analysis-export.ts](../../src/domain/analysis-export.ts)), split the same way `library-import.ts` is split from its actions. It is **deliberately lossy and not reimportable**, and the two rules that keep it honest are:

- **It is not a backup, so it must not mark one.** `markBackupCreated` is missing on purpose — `lastBackupAt` drives the reminder at the head of the plan, and a file without images, ids or the discarded sessions cannot undo a data loss. Counting it would silence the one warning that exists against the iOS home-screen deletion. `analysis-export.spec.ts` asserts "Noch nie gesichert" still stands afterwards. What the export *does* set is its own field: `copyAnalysisSnapshot` writes `lastAnalysisCopiedAt` via `markAnalysisCopied`, chained after the successful clipboard write (a failed copy sets nothing, and the function stays non-`async`); `describeSyncStatus` ([domain/sync-status.ts](../../src/domain/sync-status.ts)) turns it into "Seitdem: 2 Einheiten, 1 Lauf." for the reconciliation page. Never `lastBackupAt`.
- **What is filtered stays visible.** Every dropped session gets a one-line note in `meta.verworfeneSessions` (`keine abgeschlossenen Sätze`, `läuft noch`). Filtering silently and filtering visibly differ by exactly this list.

The row is *session × exercise × side*, and the rules are all in the pure module: only `completed` logs count (an unchecked row is a prescription, not a measurement); warmups are aggregated into a count, never listed; a row exists only for an exercise that was executed **or** explicitly skipped, because an exercise that never came up in an abandoned session is exactly the empty row that makes the full export unreadable; and a session under `MINIMUM_COMPLETION_RATIO` of its planned sets is exported but flagged `unvollstaendig`, with **skipped exercises out of the denominator** — skipping changes the plan of that session, it is not a miss.

`tests.csv` is the side-comparison tests (`ExerciseTest`: `leftValue`, `rightValue`, `asymmetryPercent`, `notes`), newest first, and it is a **fourth file rather than a block in `meta.json`** on purpose. Two of the three arguments for meta.json don't hold: the different grain is the *reason* for a separate file, not against it — `progression.csv` already has one — and the extra attachment costs nothing, because `createZipArchive` bundles everything into one archive anyway. What remains, "few rows", is a statement about today; a series that runs for twelve weeks is a table. Against it stands what `meta.json` is: the account *of* the export — what is in it, what was dropped. Measurements are not provenance, and hip internal rotation and the knee-to-wall side difference are the targets progress is measured against, not a footnote in the file's own description. The exercise name comes from `exerciseNameSnapshot` and is deliberately **not** looked up via `exerciseId` — that is what the snapshot is for; a renamed or deleted exercise would otherwise cost a measurement that actually happened. Tests hang off no session and are therefore never dropped with one: they are taken independently of training.

**`meta.uebungen` describes the library, not the past.** Its `trackingMode` used to come from the session snapshot, which reads like a statement about today and is one about history: switch the Nordic Curl from `time` to `reps_weight` and you are left with 27 old snapshots saying `time` and two new ones saying `reps_weight` — the export reported the majority. An analysis read that, concluded the switch had never reached the device, and recommended it a second time. `describeTrackingMode` therefore takes the **current** value from `Exercise` (which is why `AnalysisExportInput` carries the library at all) and puts any differing snapshots beside it as `trackingModeHistorisch` — the same distinction `isLegacyExecution` ([progress.ts](../../src/domain/progress.ts)) already makes internally when the chart silently drops old executions. Matching is by **name**, like everywhere in the import, because the export carries no ids; a renamed or deleted exercise falls back to its snapshot, which is then the best answer available.

Two limits of the format are worth knowing before trusting a reading of it, because both have already produced wrong conclusions. `sessions.csv` carries only the **top set** per session × exercise × side, so a ramp inside one session (20×12 → 40×12 → 50×8) shows up as a single `50×8` and looks like a jump against last week — `arbeitssaetze` is the tell. And what the device *prescribes* lives in two files of its own and nowhere else: `plan.csv` (which workout or run is due on which day, below) and `bestand.json` (the composition of every workout, below). For `sessions.csv` "not in the data" still means "not executed in these sessions", never "not in the plan".

Three details that look like deviations and are not. **Numbers use a decimal point**, not `formatNumber`'s German comma — the German comma is the convention for every *rendered* number in this app, and in a comma-separated file it would be a separator. The **top set** ranks by weight → band → height → seconds → reps: the brief says "highest weight, ties by reps", which for an exercise without kilos would not be a choice but an accident, and where only weight and reps exist the ranking *is* the brief. And `std_seit_letzter_einheit_b` measures against a **template name**, the one piece of user vocabulary in the export — it is a parameter (`DEFAULT_REFERENCE_TEMPLATE_NAME`) rather than a constant in the body, and where no such workout exists the column stays empty instead of guessing.

**Runs and weeks joined the export as two more files, and a column.** `wochen.csv` is the weekly calculation (`buildWeeklyVolume`, the same rows History and the week sheet read) and `laeufe.csv` one row per run, newest first, with pace computed at export time — runs hang off no session, so like tests they are never dropped with one. `sessions.csv` gained **`art`** at the **end** (`kraft` / `mobility`, from `templateCategorySnapshot`); appending keeps every positional reader of the old file working. `meta.json` carries `laeufe.anzahl` and a `hinweise` list — reading notes that belong to the file's account of itself (`kraft_dauer_min` includes pauses; `wochen.csv` counts completed sessions only). **`analysis-export.ts` contains a NUL control character** (the key joiner in the progression grouping), so `grep` treats it as binary: search it with `grep -a`.

**The dated plan joined as `plan.csv`, plus a column on each side.** One row per entry, **including future ones** — `meta.zeitraum` derives from sessions and would cut off exactly the entries a planning conversation needs — with `datum, reihenfolge, art` (`kraft` / `mobility` / `lauf`), the name, the run targets (`soll_*`), `notiz` and `status`: `erledigt`, `offen` (today or later) or `verstrichen` (past and not done). A *taken* entry whose session is still running counts as not done. `verstrichen` does not mean skipped, only "nothing was linked to it" — the unit may well have been trained without matching, in another week — and `meta.json` says so in `hinweise`, beside `plan.anzahl` and the count per status. `sessions.csv` gained `geplant_am` (from `planDateSnapshot`) and `laeufe.csv` `geplant_am` plus `plan_titel` (from `runPlanSnapshot`), again **appended at the end** so positional readers keep working.

**The library's current state joined as `bestand.json`** — built by the pure `buildLibraryInventory` ([library-inventory.ts](../../src/domain/library-inventory.ts)): every exercise with `trackingMode` / `unilateral` / `loadKind` / `tracksHeight` / instructions, every workout with its assignments (dense `orderIndex`, `workSetCount`, targets, rest, notes, supersets as `S1`, `S2` … per workout), the band catalogue and the active program's weeks with their progression rules; a guided workout carries its `steps`, because an import replaces that list whole and so claude.ai has to know the current one. It exists because the plan is now written in a claude.ai project as library-import files, and every exercise entry needs the exact name plus `trackingMode` and `unilateral` (a wrong value silently switches the exercise), every assignment its `orderIndex` and `workSetCount` — none of which the training files carry, and `meta.uebungen` only lists what was trained. Three rules hold it up. It uses **the import's field names**, so rows move into an import file without translation — `library-inventory.test.ts` reads the inventory back as an import with `replaceAssignments` and requires *no change at all*, which is the proof rather than the claim. It carries **no `schemaVersion`**, so the app rejects it if someone imports it unchanged. And it has **no ids**, like the rest of the export; `targetBand` and `programm` are information only (the import cannot set either) and the file's `hinweis` says so. Plan entries are deliberately not repeated there — that is `plan.csv`.

Beside the archive stands **`copyAnalysisSnapshot`** — the same eight files as one text block on the clipboard, assembled by the pure `buildAnalysisPasteText`. The ZIP is the longer way round on a phone (save it, switch app, hunt for the attachment), and an archive frequently is not unpacked at the other end; the library import has carried a paste field next to its file picker for exactly that reason, and this is the missing half of it. `meta.json` goes **first** and `bestand.json` last, because it holds the period, the effective week with `weekOverrideAktiv` and each exercise's `trackingMode` — read the table before that and seconds get summed into reps. Two things are load-bearing. The function is deliberately **not `async`**: WebKit grants clipboard access only inside the user gesture, and an `await` before the call ends it, so `writeText(await …)` fails *silently* on the phone while it works in desktop Chrome — the same class of bug as `prepareMediaAsset`, where the `File` has to be read before the transaction opens. The way out is `ClipboardItem` with a **Promise** as its value: the call happens synchronously inside the gesture, the data may follow. And `loadAnalysisFiles` sits under both paths, so the archive and the clipboard can never disagree about what the export contains.

The archive is written by [lib/zip.ts](../../src/lib/zip.ts), store-only and dependency-free: eight files are one share sheet on iOS instead of eight, and at this size deflate would buy nothing that a dependency does not cost back. `createZipBytes` stands beside `createZipArchive` because jsdom's `Blob` has no `arrayBuffer()`, so the structure would otherwise only be checkable in a browser.

### The library import — a second, much smaller import

The import section sits on `/sync` ("Abgleich"), not in Settings, beside "Analyse kopieren": the project in claude.ai is where the file comes from, and the same page sends the current state back. The last five `LibraryImportLog` rows are listed once, under it, by `SyncPage` ("Letzte Importe", as in the mockup) — `LibraryImportSection` itself no longer lists them, so there is exactly one history. Each row's text comes from the pure `describeImportCounts` ([library-import-summary.ts](../../src/domain/library-import-summary.ts), unit-tested), which counts *every* field of the log (workouts, exercises, assignments, band levels, plan entries, plus "n … entfernt" for removed assignments and plan entries) so an import that only removed appointments or created band levels never reads "keine Änderungen".

The backup restore replaces everything. The **library import** ([domain/library-import.ts](../../src/domain/library-import.ts) + [db/library-import-actions.ts](../../src/db/library-import-actions.ts), UI in [LibraryImportSection.tsx](../../src/components/LibraryImportSection.tsx)) adds to what is there: exercises, workouts, their assignments, band levels and dated plan entries, out of a hand-written JSON file. Set logs, tests and settings are not even in its transaction — what it cannot reach, it cannot damage — and sessions and runs are in it only to be *read*, because which plan entries are taken is derived from them. Ready payloads live **outside the repository**, under `~/Documents/gym-book-daten/import/`: this repository is public, and the payloads carry exercise instructions with medical reasoning (injury history, contraindications) — as does the analysis context beside them. `.gitignore` still lists `docs/import/` as a tripwire in case someone recreates it here. The same rule is why they were never in `public/`, which would deploy and precache them. If you need an example payload in the repo, write a synthetic one; do not un-ignore the directory.

Five rules carry it, and each one is a bug that a name-based import invites:

- **Matched by name, not by id** — `normalizeImportKey` (trimmed, `toLocaleLowerCase('de')`) is the one place that decides identity. A file written by hand does not know the device's UUIDs, and "Nordic Curl" must not become a second exercise next to "nordic curl".
- **Only the named fields are written.** A missing key is not a deletion — the same rule as `updateSetLogValues`, for the same reason (`Table.update` treats `undefined` as *delete this property*). Running the same file twice therefore changes nothing, which is what makes the import repeatable.
- **Nothing is deleted unless the file asks for it, and then only assignments and plan entries.** Without a flag, existing rows keep their **position**: a target `orderIndex` decides where something *new* is inserted, everything from that index on shifts back, and the block is renumbered densely. An assignment that already exists stays where the arrows in the workout put it, and the preview says so. An insertion that would land inside a superset moves to the end of that run — group members must stay contiguous ([superset.ts](../../src/domain/superset.ts)). A workout carrying **`replaceAssignments: true`** is the other mode: its assignments in the file are the complete target *composition* — what is missing is removed (`removed`, red `ENTFERNT` in the preview, its progression rules go with it exactly as in `deleteTemplateExercise`), the file's order applies densely, and supersets come from a per-workout group name (`superset`), which is rejected on a workout without the flag rather than guessed. An assignment that stays keeps its **id**, so its weekly rules survive, and a group keeps its `supersetGroupId` when its members are unchanged — that is what keeps a second run "unverändert". Replacing is about composition, not values: a missing key still changes nothing, and only an explicit `null` clears a target field (the one place where `Table.update` dropping an `undefined` property is the point). The import aborts on a flagged workout with no rows in the file — a typo in its name must not empty a workout — on a doubled `orderIndex`, and on a group that is split or has one member. Exercises, workouts and band levels themselves are never removed by an import. A preview with removals — assignments or plan entries — downloads a full backup (`exportDatabaseSnapshot()`, the same safety net as the restore in Settings) **before** writing — removed progression rules cannot be re-imported — and a failed backup aborts the import.
- **Validation aborts, it does not warn.** An unknown `trackingMode`, a missing required field, a reference to a workout or exercise that neither exists nor is created by the same file: the import stops with that line named ("Zuordnung 3: Workout ‚Einheit C' gibt es nicht …"). Half an import is worse than none.
- **Planned twice, written once.** `planLibraryImport` is pure: it takes the payload plus the current state as plain arrays and returns entries carrying both the preview text (`NEU` / `AKTUALISIERT` with *field: old → new* / `UNVERÄNDERT`) and the values to write. `applyLibraryImport` re-plans **inside** its transaction rather than executing the preview — between preview and confirmation an exercise may have been created or renamed, and a plan against a stale state creates twins. Same reasoning as the active-session check inside `startSessionFromTemplate`.

**Plan entries** come as an optional `planEntries` block ([plan-import.ts](../../src/domain/plan-import.ts), planned by `planPlanEntries`), each carrying **exactly one** of `workout` (a name, resolved like an assignment's, so a workout created by the same file counts) or `run` (title plus targets). Identity is `planEntryKey`, so the same file twice is *unverändert*. Without `planRange` the file only adds and updates; **with `planRange`** (both ends included) it is the complete plan of that period, and open entries in it that the file does not name are removed (`ENTFERNT`). **Taken entries are history here too**: never changed, never removed, shown as unchanged whatever the file says. Within a day, `orderPlanDay` gives each taken entry a **fixed slot** among the day's remaining entries; the free slots are filled first by the open entries the file does not name (in their old order), then by the file's entries in file order — planning and writing both call it with the same data, so the preview names exactly the order that will stand. The abort reasons are the usual named lines: unknown workout, invalid date, a key twice in the file, an entry outside `planRange`, `from` after `to`, both or neither of `workout`/`run`, and `planRange` without `planEntries` (which would otherwise empty the period). `planEntries` deliberately carries **no `.default([])`** in the payload schema: the hash runs over the *parsed* payload, so a default would put a key into every old file and change its `payloadHash`, and "same file as last time" would stop being true for every file written before plans existed. The field-diff helpers both planners share live in [import-diff.ts](../../src/domain/import-diff.ts), a module of their own because `library-import.ts` calls the plan planner at runtime and the reverse import would be a cycle. `LIBRARY_IMPORT_SCHEMA_VERSION` stays `1` — the block is additive.

**Guided steps** come as an optional `steps` list on a template block (see "Guided templates") under the same no-`.default` rule: the golden hash in [library-import.test.ts](../../src/domain/library-import.test.ts) pins that a file without steps keeps its hash. A file that names `steps` replaces the stored list completely, one without the key leaves it; `steps` and assignments for the same workout abort the import, whether both are in the file or one of them is already in the app. The preview shows `Schritte: — → geführt, 12 Schritte`.

Every run writes a `LibraryImportLog` row (timestamp, source, counts, `payloadHash`) — after the fact nothing on the records themselves says when they arrived or from what. The hash is FNV-1a over a key-sorted serialization, so reformatting the file does not change it; it answers "same file as last time", not "has anyone tampered with this".

### One-off data fixes

[db/data-fix-actions.ts](../../src/db/data-fix-actions.ts) holds corrections to data that is already on the device — never a Dexie `upgrade()`, because each of them reinterprets training data and that needs a question first. Each sits behind a `ConfirmDialog` in Settings. **"Already done" is derived from the data, not stored**: `describeDataFixes` reads the state and the button disables itself. A stored flag would lie after restoring an older backup.

`applyNordicCurlTrackingFix` switches the exercise from `time` to `reps_weight` — seconds reward a static hold, which is exactly what this exercise must not reward. Logged seconds stay; nothing is converted. Which is why `isLegacyExecution` ([progress.ts](../../src/domain/progress.ts)) exists: a session exercise carries its own `trackingMode` snapshot, so after such a switch the old executions no longer hold the number the chart asks for and `buildProgressSeries` drops them **silently**. The exercise detail names that gap ("3 frühere Ausführungen wurden als „Zeit" erfasst …") and badges those rows "Altdaten" — in neutral ink, because that state is neither done nor skipped nor up next.

`applyWeekdaysToPlanMigration` turns the old `scheduledWeekdays` into dated plan entries and removes the field; its rules are in "The dated plan" above.

### What stays out of the backup

`ttsConfig` (Google key, voice, free quota, price, monthly character counter) and `announcements` (generated MP3s) are **not** read by `createDatabaseSnapshot` or the analysis export, and `restoreDatabaseSnapshot` neither clears nor writes them — a smuggled `ttsConfig` key in a backup file is stripped by the Zod schema. Only the local reset empties them (it clears every table). [export-tts.test.ts](../../src/lib/export-tts.test.ts) searches the serialized backup, the analysis archive and the pasted analysis text for the key string.
